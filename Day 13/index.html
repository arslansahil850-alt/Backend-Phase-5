Day 13: Search Functionality

Users expect a search bar in almost every application—whether finding open-source projects, browsing courses, or locating support articles. Building search naively by dropping raw req.query.q straight into a regular expression can crash your database with syntax errors when a user searches for C++, freeze CPU threads via ReDoS (Regular Expression Denial of Service), or force slow full-collection scans across 100,000 documents. Today you will learn how to validate and escape search inputs safely, leverage MongoDB text indexes and relevance scoring, combine search cleanly with Day 12 filters and pagination, and know when dedicated search engines are worth adopting.

Learning Objectives

By the end of Day 13, you will be able to:

  • Design clean search query parameters (e.g., ?q=...) with strict length and type validation.
  • Escape special regular-expression characters to prevent crashes and ReDoS attacks.
  • Compare unanchored regex matching, anchored prefix regex matching, and MongoDB $text indexes.
  • Configure weighted MongoDB text indexes and sort search results by relevance (textScore) with deterministic _id tie-breakers.
  • Combine search seamlessly with category/status filters and pagination metadata.
  • Evaluate search performance trade-offs and identify when dedicated search tools (Atlas Search, Meilisearch, Typesense, Elasticsearch) are needed.

Prerequisites

Before starting Day 13, make sure you understand:

  • Day 12 Concepts: Offset pagination (page, limit, skip), allow-listed filtering, and parallel Promise.all queries.
  • Days 3 & 6 Concepts: Mongoose schemas, indexes, and strict server-side input validation.

Important Terminology and Definitions

ReDoS (Regex Denial of Service)

A vulnerability where an attacker sends crafted regex characters or catastrophic backtracking patterns inside a search string, locking up database or Node.js CPU cores.

Regex Escaping

Prefixing special regex metacharacters (such as +, *, ?, (, [, $) with backslashes so inputs like "C++" or "node.js" match literal text safely.

MongoDB Text Index ($text)

A specialized index that tokenizes words, removes common stop words (like "the", "and"), applies language stemming, and enables fast keyword search via $text: { $search }.

Relevance Score (textScore)

A numeric weight calculated by MongoDB via { $meta: 'textScore' } indicating how strongly a document matches the search keywords based on term frequency and field weights.

Prefix Regex (/^term/i)

A regular expression anchored to the beginning of a string with ^. Unlike unanchored /term/i, a case-sensitive or collation-matched prefix regex can use a standard B-tree index.

Dedicated Search Engine

Purpose-built search platforms—such as MongoDB Atlas Search, Elasticsearch, Typesense, or Meilisearch—offering fuzzy typo tolerance, instant autocomplete, synonyms, and faceted search.

Detailed Theory and Explanations

1. Search Requirements & Query Parameters

Most APIs accept search keywords through a dedicated query parameter such as ?q=express+api (or ?search=...). Always validate that q is a primitive string (never an object or array from query parsing like ?q[$ne]=1), trim whitespace, collapse excessive spaces, and enforce sensible length bounds—for instance, minimum 2 characters (optional if listing all) and maximum 80–100 characters.

2. Escaping & Safely Handling User Input

Never pass raw user text straight into new RegExp(req.query.q, 'i') or { $regex: req.query.q }! If a learner searches for C++ or (express, an unescaped regex throws SyntaxError: Invalid regular expression because + and ( are regex operators. Worse, crafted nested patterns can cause catastrophic CPU backtracking (ReDoS) on both Node.js and MongoDB.

Always escape every regex metacharacter using: str.replace(/[.*+?^${}()|[\]\\]/g, '\\$&') before constructing a RegExp!

3. Regex Matching vs. MongoDB Text Search ($text)

Technique How It Matches Strengths & Trade-Offs
MongoDB $text Index Tokenizes words, stems roots (e.g., "building" matches "build"), ranks by weighted textScore. Fast indexed search across multiple fields with relevance ranking; however, only one text index is allowed per collection, and it does not match mid-word substrings (e.g., "exp" won't match "express").
Anchored Prefix Regex (/^term/i) Matches strings starting with the typed prefix. Great for exact title/SKU autocomplete; can leverage B-tree indexes (especially with case-insensitive collation or normalized lowercase field).
Unanchored Regex (/term/i) Matches substring anywhere in a field. Easy partial-word matching on small datasets (e.g., "exp" finds "Express"), but forces a full collection scan across large collections—slow without limits or filters!

4. Combining Search with Filters, Sorting & Pagination

Users rarely just search globally—they type ?q=authentication&category=backend&difficulty=intermediate&page=1&limit=10&sort=relevance. In Mongoose, you combine search conditions with allow-listed Day 12 filters inside the same filter object:

  • When q is present with a $text index, set filter.$text = { $search: cleanQuery } alongside filter.category = 'backend'.
  • To sort by relevance, project { score: { $meta: 'textScore' } } and call .sort({ score: { $meta: 'textScore' }, _id: -1 }). Notice how _id still serves as our deterministic tie-breaker!
  • When q is omitted, fall back cleanly to normal listing sorted by newest or user-selected sort key.

5. When Dedicated Search Services Are Useful

MongoDB text indexes and escaped prefix searches cover many small-to-medium apps well. However, dedicated search engines—such as MongoDB Atlas Search (Lucene-powered inside Atlas), Meilisearch, Typesense, or Elasticsearch / OpenSearch—become worthwhile when your product needs:

  • Typo tolerance (fuzzy matching): Searching "expres midleware" still finds "Express Middleware".
  • Instant search-as-you-type autocomplete across hundreds of thousands of products.
  • Synonyms & multi-language ranking: Treating "JS" and "JavaScript" or "laptop" and "notebook" as related.
  • Faceted aggregation counts: Showing exact filter counts (e.g., Backend (42), Security (18)) alongside results.

Step-by-Step Tutorial: Sample Projects Search API

Let us build a complete search API for a collection of sample developer projects in Node.js, Express.js, and Mongoose—supporting weighted MongoDB text search, safe prefix fallback, allow-listed filtering, relevance sorting, and pagination.

Step 1: Create the Project Model with a Weighted Text Index (src/models/Project.js)

Assigning higher weights to title (10) and tags (5) than summary (2) ensures a keyword match in a project's title ranks above an incidental mention in its summary.

Backend Source Code: src/models/Project.js (Runs on Node.js)

import mongoose from 'mongoose';

const projectSchema = new mongoose.Schema(
  {
    title: { type: String, required: true, trim: true, maxlength: 120 },
    summary: { type: String, required: true, trim: true, maxlength: 600 },
    category: {
      type: String,
      required: true,
      enum: ['backend', 'fullstack', 'security', 'devops'],
      index: true
    },
    difficulty: {
      type: String,
      required: true,
      enum: ['beginner', 'intermediate', 'advanced'],
      index: true
    },
    tags: [{ type: String, trim: true, lowercase: true }],
    stars: { type: Number, default: 0, min: 0 }
  },
  { timestamps: true }
);

projectSchema.index(
  { title: 'text', tags: 'text', summary: 'text' },
  {
    weights: { title: 10, tags: 5, summary: 2 },
    name: 'project_text_search_idx'
  }
);

projectSchema.index({ category: 1, difficulty: 1, stars: -1, _id: -1 });

const Project = mongoose.model('Project', projectSchema);

export default Project;

Step 2: Create Search Validation & Regex Escaping Utilities (src/utils/searchHelpers.js)

Always validate string type and length bounds, and provide an explicit regex escaper whenever prefix or substring matching is needed safely.

Backend Source Code: src/utils/searchHelpers.js (Runs on Node.js)

export const escapeRegex = (input) => {
  return String(input).replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
};

export const parseSearchQuery = (rawQuery, { minLength = 2, maxLength = 80 } = {}) => {
  if (rawQuery === undefined) {
    return null;
  }

  if (typeof rawQuery !== 'string') {
    const err = new Error('Search query "q" must be a text string.');
    err.statusCode = 400;
    throw err;
  }

  const normalized = rawQuery.trim().replace(/\s+/g, ' ');
  if (normalized.length === 0) {
    return null;
  }

  if (normalized.length < minLength) {
    const err = new Error(`Search query "q" must be at least ${minLength} characters.`);
    err.statusCode = 400;
    throw err;
  }

  if (normalized.length > maxLength) {
    const err = new Error(`Search query "q" cannot exceed ${maxLength} characters.`);
    err.statusCode = 400;
    throw err;
  }

  return normalized;
};

Step 3: Implement Search + Filter + Pagination Service (src/services/projectSearchService.js)

Notice how the service combines $text search with allow-listed category and difficulty filters, supports both relevance sorting and standard sorting, and also provides an autocomplete prefix search endpoint using escapeRegex!

Backend Source Code: src/services/projectSearchService.js (Runs on Node.js) 

import Project from '../models/Project.js';
import { escapeRegex, parseSearchQuery } from '../utils/searchHelpers.js';
import { parsePaginationParams, buildPaginationMeta } from '../utils/pagination.js';

const ALLOWED_CATEGORIES = new Set(['backend', 'fullstack', 'security', 'devops']);
const ALLOWED_DIFFICULTIES = new Set(['beginner', 'intermediate', 'advanced']);

export const searchProjects = async (query) => {
  const keyword = parseSearchQuery(query.q);
  const { page, limit, skip } = parsePaginationParams(query, {
    defaultLimit: 10,
    maxLimit: 40
  });

  const filter = {};

  if (query.category !== undefined) {
    const cat = String(query.category).trim().toLowerCase();
    if (!ALLOWED_CATEGORIES.has(cat)) {
      const err = new Error('Invalid category filter.');
      err.statusCode = 400;
      throw err;
    }
    filter.category = cat;
  }

  if (query.difficulty !== undefined) {
    const diff = String(query.difficulty).trim().toLowerCase();
    if (!ALLOWED_DIFFICULTIES.has(diff)) {
      const err = new Error('Invalid difficulty filter.');
      err.statusCode = 400;
      throw err;
    }
    filter.difficulty = diff;
  }

  if (keyword) {
    filter.$text = { $search: keyword };
  }

  const requestedSort = typeof query.sort === 'string' ? query.sort.trim() : 'default';

  let projection = '-__v';
  let sortSpec = { createdAt: -1, _id: -1 };

  if (keyword && (requestedSort === 'default' || requestedSort === 'relevance')) {
    projection = { title: 1, summary: 1, category: 1, difficulty: 1, tags: 1, stars: 1, createdAt: 1, score: { $meta: 'textScore' } };
    sortSpec = { score: { $meta: 'textScore' }, _id: -1 };
  } else if (requestedSort === 'stars_desc') {
    sortSpec = { stars: -1, _id: -1 };
  } else if (requestedSort === 'newest' || requestedSort === 'default') {
    sortSpec = { createdAt: -1, _id: -1 };
  } else {
    const err = new Error('Invalid sort option. Allowed: relevance, newest, stars_desc');
    err.statusCode = 400;
    throw err;
  }

  const [projects, totalItems] = await Promise.all([
    Project.find(filter)
      .select(projection)
      .sort(sortSpec)
      .skip(skip)
      .limit(limit)
      .lean(),
    Project.countDocuments(filter)
  ]);

  const pagination = buildPaginationMeta({ totalItems, page, limit });
  pagination.countOnPage = projects.length;

  return {
    queryApplied: keyword,
    pagination,
    data: projects
  };
};

export const autocompleteProjectTitles = async (rawPrefix) => {
  const prefix = parseSearchQuery(rawPrefix, { minLength: 1, maxLength: 40 });
  if (!prefix) {
    return [];
  }

  const safePattern = new RegExp(`^${escapeRegex(prefix)}`, 'i');

  return Project.find({ title: safePattern })
    .select('title category difficulty')
    .sort({ stars: -1, _id: -1 })
    .limit(8)
    .lean();
};

Step 4: Wire Controllers and Test Search Queries

Backend Source Code: src/controllers/projectController.js (Runs on Node.js) 

import { searchProjects, autocompleteProjectTitles } from '../services/projectSearchService.js';

export const getProjects = async (req, res, next) => {
  try {
    const result = await searchProjects(req.query);
    return res.status(200).json({
      status: 'success',
      query: result.queryApplied,
      pagination: result.pagination,
      data: result.data
    });
  } catch (err) {
    return next(err);
  }
};

export const getTitleSuggestions = async (req, res, next) => {
  try {
    const suggestions = await autocompleteProjectTitles(req.query.q);
    return res.status(200).json({
      status: 'success',
      count: suggestions.length,
      data: suggestions
    });
  } catch (err) {
    return next(err);
  }
};

Common Mistakes, Security Notes, and Best Practices

Common Search Mistakes

  • Passing unescaped req.query.q to new RegExp(): Searching "C++" or "[test" throws an unhandled SyntaxError and exposes your API to ReDoS CPU freezes.
  • Trying to create two separate text indexes on one collection: MongoDB allows only one text index per collection; include all searchable text fields inside a single compound text index with weights.
  • Sorting by textScore when $text is NOT in the filter: Calling { $meta: 'textScore' } without an active $text query throws a MongoDB error!
  • Using unanchored /term/i on giant collections: Forces MongoDB to scan every document on disk rather than using an index.

Security & Best-Practice Notes

  • Always check typeof q === 'string': Prevents attackers from sending ?q[$ne]=secret objects via Express's extended query parser.
  • Cap search query length: Limit q to ~80–100 characters so overly long search strings cannot waste regex or tokenization CPU.
  • Always escape regex metacharacters: Use escapeRegex(input) before every RegExp construction.
  • Always paginate search results: Never return unlimited search matches; combine search with Day 12 pagination and _id tie-breakers.

Hands-On Exercises

  1. Metacharacter Safety Test: Send ?q=C%2B%2B+(v2) (URL-encoded C++ (v2)) to your autocomplete endpoint and confirm escapeRegex prevents any SyntaxError.
  2. Type Validation Test: Send ?q[$gt]=a to your search endpoint and confirm parseSearchQuery rejects the non-string object with 400 Bad Request.
  3. Weight Tuning Experiment: Create two sample projects—one with "Redis" in the title and one with "Redis" only in the summary—and confirm sort=relevance places the title match first.
  4. Empty-Search Graceful Fallback: Call GET /api/v1/projects?q=%20%20%20 (only whitespace) and verify it cleanly treats the query as empty and returns normal paginated projects without throwing a MongoDB $text error.

Short-Answer Questions

Think through each answer carefully before opening the explanation.

1. Why must user search strings be escaped before passing them into new RegExp()?

Characters like +, *, ?, (, and [ have special meanings in regular expressions. Unescaped inputs crash on syntax errors (like searching "C++") and can trigger ReDoS CPU exhaustion.

2. How does MongoDB's $text index handle word variations like "developing" and "developer"?

MongoDB's text index tokenizes text, strips stop words, and applies language stemming so related word stems match cleanly, while ranking results using weighted textScore.

3. Why should search endpoints always enforce length bounds and string type checks on req.query.q?

Type checking blocks NoSQL operator objects (like ?q[$ne]=1), minimum length checks avoid overly broad 1-letter scans, and maximum length caps protect tokenization and regex CPU time.

4. How can search be combined cleanly with Day 12 filters and pagination?

Include filter.$text = { $search: keyword } inside the same filter object as allow-listed fields like category, then pass that unified filter to both find(filter).skip().limit() and countDocuments(filter) via Promise.all.

5. Name three features that justify migrating from MongoDB $text to a dedicated search engine.

Fuzzy typo tolerance (matching misspelled words), fast partial-word autocomplete at scale, custom synonyms, and real-time faceted filter counts.

Day 13 Revision Summary

  • Validate search query strings strictly for type and length bounds (e.g., 2–80 characters).
  • Always escape regex metacharacters with escapeRegex() to prevent syntax crashes and ReDoS attacks.
  • Use weighted MongoDB $text indexes for fast multi-field keyword search and textScore relevance ranking (remembering only one text index is allowed per collection).
  • Combine search filters, allow-listed category filters, pagination, and _id tie-breakers inside one unified Promise.all query flow.
  • Adopt dedicated search engines (Atlas Search, Typesense, Meilisearch, Elasticsearch) when typo tolerance, synonyms, and large-scale faceted autocomplete are required.
