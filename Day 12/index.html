Day 12: Pagination and Filtering

Calling Model.find() with no limits works fine when your database has 12 sample items. Once a real MongoDB collection grows to 50,000 products or 200,000 orders, returning every document in one HTTP response spikes server RAM, stalls Node.js JSON serialization, saturates network bandwidth, and freezes the user's browser. Production APIs deliver data in predictable slices using pagination, filtering, and stable sorting. Today you will master offset-based pagination in MongoDB, query validation, allow-listed filtering and sorting, tie-breaker stability, and rich pagination metadata.

Learning Objectives

By the end of Day 12, you will be able to:

  • Explain why unbounded find() queries hurt database, server, network, and client performance.
  • Implement offset-based pagination using page and limit query parameters and MongoDB's .skip() and .limit().
  • Validate query inputs strictly and enforce safe default and maximum page sizes.
  • Build allow-listed filtering (exact match, boolean, and numeric range filters like minPrice/maxPrice) without exposing raw Mongoose queries.
  • Implement allow-listed, stable sorting using _id as a tie-breaker so items never jump or duplicate across pages.
  • Return complete pagination metadata (totalItems, totalPages, currentPage, limit, hasNextPage, hasPrevPage) using parallel Promise.all queries.
  • Understand when deep-offset skip() slows down and how cursor-based pagination solves deep scrolling.

Prerequisites

Before starting Day 12, make sure you understand:

  • Days 1, 3, 4 & 6 Concepts: Reading req.query strings, MVC/service layering, Mongoose queries, and preventing NoSQL injection.
  • MongoDB Query Operators: Familiarity with comparison operators like $gte and $lte, plus countDocuments().

Important Terminology and Definitions

Offset-Based Pagination

Dividing results into numbered pages using page and limit, skipping (page - 1) * limit records before returning up to limit documents.

Page Size Bounds

A sensible default (e.g., 10) when limit is omitted, paired with a strict server maximum (e.g., 50) so a client cannot request ?limit=999999.

Allow-Listed Filtering

Explicitly checking and mapping known query parameters (such as category, inStock, minPrice) instead of passing raw req.query into Model.find(req.query).

Stable Sorting

Adding a unique secondary sort field—always _id in MongoDB—so ties in primary sort values (like two products with identical prices) always appear in the same deterministic page order.

Pagination Metadata

Summary fields returned alongside data—such as totalItems, totalPages, currentPage, hasNextPage, and hasPrevPage—so frontends can render page buttons accurately.

.lean()

A Mongoose query option that returns plain lightweight JavaScript objects instead of heavy hydrated Mongoose Document instances—cutting memory and CPU overhead on read-only list endpoints.

Detailed Theory and Explanations

1. Why Large Unbounded API Responses Are Inefficient

Returning an entire collection on GET /api/v1/products creates bottlenecks at every tier:

  • Database Tier: MongoDB reads thousands of documents from disk/cache and streams massive BSON payloads over the network to Node.js.
  • Node.js Server Tier: Hydrating 20,000 Mongoose Documents and calling JSON.stringify() blocks the single JavaScript event loop thread, slowing down all other users!
  • Client Tier: Mobile browsers waste data downloading megabytes of items the user never scrolls to.

2. Offset-Based Pagination Math: page, limit, and skip

Given a validated positive integer page (starting at 1) and a bounded integer limit (say, 10):

Page Requested Formula: skip = (page - 1) * limit MongoDB Slice Returned
?page=1&limit=10 (1 - 1) * 10 = 0 Items 1 through 10
?page=2&limit=10 (2 - 1) * 10 = 10 Items 11 through 20
?page=3&limit=10 (3 - 1) * 10 = 20 Items 21 through 30

And total pages is calculated using Math.ceil(totalItems / limit) (returning 0 or 1 cleanly when totalItems === 0).

3. Query Validation, Defaults, and Maximum Page Sizes

Remember that values inside req.query are untrusted strings. Without validation, a user sending ?page=-3 passes a negative number to .skip(-40) (crashing MongoDB!), sending ?page=abc produces NaN, and sending ?limit=500000 bypasses pagination completely!

Always parse integers strictly, reject invalid negative/non-numeric inputs with 400 Bad Request (or clamp thoughtfully depending on API contract), apply a safe default like DEFAULT_LIMIT = 10, and enforce a hard ceiling like MAX_LIMIT = 50.

4. Safe Filtering & Sorting (Allow-Listing)

A common beginner anti-pattern is writing Model.find(req.query). Never do that! First, query keys like page, limit, and sort are not document fields, so MongoDB would find zero matches. Second, an attacker could query private fields (like ?passwordResetToken=...) or inject MongoDB operators!

Instead, construct a clean filter object from explicit allow-listed fields (e.g., category, inStock, minPrice, maxPrice) and map sort strictly through an allow-list dictionary such as:

  • newest → { createdAt: -1, _id: -1 }
  • price_asc → { price: 1, _id: 1 }
  • price_desc → { price: -1, _id: -1 }
  • rating_desc → { rating: -1, _id: -1 }

5. Stable Sorting & Tie-Breaker Concern

Suppose 15 products all cost $25, and you run .sort({ price: 1 }).skip(10).limit(10) without a tie-breaker. Because MongoDB does not guarantee a consistent order among tied documents across separate queries, item #10 on Page 1 might shift into slot #11 on Page 2—causing users to see duplicate items or miss items completely when clicking "Next Page"! Including unique _id as the final sort key guarantees deterministic, stable pagination.

6. Efficient Database Queries & Trade-Off of Deep skip()

To build pagination metadata efficiently, execute the paginated data query and Model.countDocuments(filter) concurrently using Promise.all([...]) instead of waiting sequentially. Add .lean() and .select('-__v') to the list query, and create MongoDB compound indexes matching your common filter + sort fields.

Trade-off to know: In MongoDB, .skip(500000) still forces the database to scan and discard the first 500,000 index entries before returning 10 items. For typical catalogs, dashboards, and admin tables (pages 1–200), offset pagination is ideal because users can jump directly to any page number. For infinite social feeds with millions of rows, cursor-based (keyset) pagination (e.g., ?afterId=... using _id: { $lt: lastSeenId }) stays fast at any depth.

Step-by-Step Tutorial: Paginated, Sortable, Filterable Endpoint

Let us build a complete paginated, sortable, filterable product-catalog API using Node.js, Express.js, and Mongoose. All backend code below runs on Node.js (server-side).

Step 1: Define the Mongoose Schema with Supporting Indexes (src/models/Product.js)

Adding compound indexes on common filter + sort combinations prevents slow full-collection scans.

Backend Source Code: src/models/Product.js (Runs on Node.js)

import mongoose from 'mongoose';

const productSchema = new mongoose.Schema(
  {
    name: { type: String, required: true, trim: true },
    category: {
      type: String,
      required: true,
      enum: ['audio', 'laptops', 'accessories', 'monitors'],
      index: true
    },
    price: { type: Number, required: true, min: 0 },
    rating: { type: Number, default: 4.0, min: 1, max: 5 },
    inStock: { type: Boolean, default: true, index: true }
  },
  { timestamps: true }
);

productSchema.index({ category: 1, inStock: 1, price: 1, _id: 1 });
productSchema.index({ createdAt: -1, _id: -1 });

const Product = mongoose.model('Product', productSchema);

export default Product;

Step 2: Create a Reusable Query Validation & Pagination Helper (src/utils/pagination.js)

Centralizing pagination parsing guarantees consistent defaults, maximum caps, and metadata formulas across every list endpoint in your API.

Backend Source Code: src/utils/pagination.js (Runs on Node.js)

export const parsePaginationParams = (query, { defaultLimit = 10, maxLimit = 50 } = {}) => {
  let page = 1;
  let limit = defaultLimit;

  if (query.page !== undefined) {
    const parsedPage = Number(query.page);
    if (!Number.isInteger(parsedPage) || parsedPage < 1) {
      const err = new Error('Query parameter "page" must be a positive integer.');
      err.statusCode = 400;
      throw err;
    }
    page = parsedPage;
  }

  if (query.limit !== undefined) {
    const parsedLimit = Number(query.limit);
    if (!Number.isInteger(parsedLimit) || parsedLimit < 1) {
      const err = new Error('Query parameter "limit" must be a positive integer.');
      err.statusCode = 400;
      throw err;
    }
    limit = Math.min(parsedLimit, maxLimit);
  }

  const skip = (page - 1) * limit;
  return { page, limit, skip };
};

export const buildPaginationMeta = ({ totalItems, page, limit }) => {
  const totalPages = totalItems === 0 ? 0 : Math.ceil(totalItems / limit);
  return {
    totalItems,
    totalPages,
    currentPage: page,
    limit,
    countOnPage: 0,
    hasNextPage: page < totalPages,
    hasPrevPage: page > 1 && totalPages > 0
  };
};

Step 3: Build the Filtering, Sorting & Query Service (src/services/productService.js)

Notice the strict allow-lists for category, inStock, numeric price bounds, and sort options—every sort includes _id as a tie-breaker.

Backend Source Code: src/services/productService.js (Runs on Node.js)

import Product from '../models/Product.js';
import { parsePaginationParams, buildPaginationMeta } from '../utils/pagination.js';

const ALLOWED_CATEGORIES = new Set(['audio', 'laptops', 'accessories', 'monitors']);

const SORT_OPTIONS = Object.freeze({
  newest: { createdAt: -1, _id: -1 },
  oldest: { createdAt: 1, _id: 1 },
  price_asc: { price: 1, _id: 1 },
  price_desc: { price: -1, _id: -1 },
  rating_desc: { rating: -1, _id: -1 }
});

const buildProductFilter = (query) => {
  const filter = {};

  if (query.category !== undefined) {
    const cat = String(query.category).trim().toLowerCase();
    if (!ALLOWED_CATEGORIES.has(cat)) {
      const err = new Error('Invalid category filter.');
      err.statusCode = 400;
      throw err;
    }
    filter.category = cat;
  }

  if (query.inStock !== undefined) {
    if (query.inStock !== 'true' && query.inStock !== 'false') {
      const err = new Error('Query parameter "inStock" must be true or false.');
      err.statusCode = 400;
      throw err;
    }
    filter.inStock = query.inStock === 'true';
  }

  const priceFilter = {};
  if (query.minPrice !== undefined) {
    const min = Number(query.minPrice);
    if (!Number.isFinite(min) || min < 0) {
      const err = new Error('Query parameter "minPrice" must be a non-negative number.');
      err.statusCode = 400;
      throw err;
    }
    priceFilter.$gte = min;
  }

  if (query.maxPrice !== undefined) {
    const max = Number(query.maxPrice);
    if (!Number.isFinite(max) || max < 0) {
      const err = new Error('Query parameter "maxPrice" must be a non-negative number.');
      err.statusCode = 400;
      throw err;
    }
    priceFilter.$lte = max;
  }

  if (priceFilter.$gte !== undefined && priceFilter.$lte !== undefined && priceFilter.$gte > priceFilter.$lte) {
    const err = new Error('"minPrice" cannot be greater than "maxPrice".');
    err.statusCode = 400;
    throw err;
  }

  if (Object.keys(priceFilter).length > 0) {
    filter.price = priceFilter;
  }

  return filter;
};

export const queryProducts = async (query) => {
  const { page, limit, skip } = parsePaginationParams(query, {
    defaultLimit: 10,
    maxLimit: 50
  });

  const sortKey = typeof query.sort === 'string' ? query.sort.trim() : 'newest';
  const sortSpec = SORT_OPTIONS[sortKey];
  if (!sortSpec) {
    const err = new Error(`Invalid sort option. Allowed: ${Object.keys(SORT_OPTIONS).join(', ')}`);
    err.statusCode = 400;
    throw err;
  }

  const filter = buildProductFilter(query);

  const [items, totalItems] = await Promise.all([
    Product.find(filter)
      .select('-__v')
      .sort(sortSpec)
      .skip(skip)
      .limit(limit)
      .lean(),
    Product.countDocuments(filter)
  ]);

  const pagination = buildPaginationMeta({ totalItems, page, limit });
  pagination.countOnPage = items.length;

  return {
    pagination,
    data: items
  };
};

Step 4: Wire the Controller and Route

Backend Source Code: src/controllers/productController.js (Runs on Node.js)

import { queryProducts } from '../services/productService.js';

export const listProducts = async (req, res, next) => {
  try {
    const result = await queryProducts(req.query);
    return res.status(200).json({
      status: 'success',
      pagination: result.pagination,
      data: result.data
    });
  } catch (err) {
    return next(err);
  }
};

Real-World Use Cases

1. E-Commerce Storefronts

Shoppers filter by category, brand, availability, and price range while sorting by price or rating, browsing 12–24 products per page effortlessly.

2. Admin Order & Audit Dashboards

Support teams inspect thousands of customer orders filtered by status (pending, shipped) and sorted newest-first with numbered page controls.

3. Mobile Infinite Scroll Feeds

Mobile apps check pagination.hasNextPage and fetch page + 1 (or cursor afterId) only when the user nears the bottom of the screen.

4. Public Developer APIs

Capping MAX_LIMIT prevents third-party API consumers from accidentally or maliciously draining your database bandwidth in a single request.

Common Mistakes, Security Notes, and Best Practices

Common Pagination & Filtering Mistakes

  • Passing req.query straight into Model.find(req.query): Breaks pagination (because page/limit are treated as document fields!) and opens NoSQL operator injection and arbitrary private-field probing.
  • No maximum limit cap: Letting users pass ?limit=1000000 defeats pagination completely and enables easy DoS attacks.
  • Sorting without a unique tie-breaker: Sorting solely on { price: 1 } causes duplicate or skipped records across page boundaries when multiple items share the same price.
  • Running find() and countDocuments() sequentially: Using two separate await lines doubles database round-trip latency; run both together with Promise.all.
  • Crashing on ?page=0 or ?page=-1: Produces a negative skip value, which MongoDB rejects with an error!

Security & Best-Practice Notes

  • Allow-list every filterable and sortable field: Never let clients pass raw field names like ?sort=passwordHash into .sort().
  • Clamp or reject absurd page numbers: Validate integer bounds cleanly before executing queries.
  • Use .lean() and .select() on list endpoints: Returns plain objects faster with lower memory usage and excludes internal fields.
  • Add MongoDB indexes: Index fields commonly combined in filter and sort so queries remain fast as collections scale.

Hands-On Exercises

  1. Boundary Input Testing: Test your paginated endpoint with ?page=0, ?page=-2, ?page=abc, ?limit=999, and ?minPrice=200&maxPrice=50. Verify invalid queries return 400 while limit=999 safely clamps to 50.
  2. Tie-Breaker Experiment: Insert 8 sample products with identical prices (e.g., $29.99), fetch pages of limit=3 with and without _id: 1 as secondary sort, and confirm deterministic ordering.
  3. Multi-Value Category Filter: Extend buildProductFilter to accept comma-separated categories (e.g., ?category=audio,monitors), validating every item against ALLOWED_CATEGORIES and mapping to { $in: [...] }.
  4. Cursor Pagination Prototype: Write a small second endpoint GET /api/v1/products/feed?limit=10&afterId=... using _id: { $lt: afterId } and compare how it avoids .skip() overhead.

Short-Answer Questions

Think through each answer carefully before opening the explanation.

1. Why are unbounded Model.find() endpoints dangerous for production APIs?

As collections grow, returning all documents at once consumes huge database I/O, spikes Node.js memory, blocks the event loop during JSON serialization, and slows down frontend rendering.

2. Explain why stable sorting requires a unique tie-breaker field such as _id.

If multiple records share identical values for the primary sort field (like price or status), MongoDB does not guarantee deterministic order among ties across separate requests—so items can duplicate or vanish between pages unless unique _id breaks ties.

3. What metadata fields help a frontend render pagination buttons cleanly?

Returning totalItems, totalPages, currentPage, limit, hasNextPage, and hasPrevPage lets UI components show total result counts, page numbers, and enabled/disabled Next/Previous buttons without guessing.

4. How should an API handle ?minPrice=200&maxPrice=50 or ?page=-1?

Both represent invalid client query parameters and should be caught during query validation and rejected cleanly with 400 Bad Request and a clear descriptive message.

5. Compare offset pagination (page/limit) vs. cursor pagination (afterId).

Offset pagination allows jumping directly to any page number and works great for dashboards and catalogs, though deep skip() offsets slow down on massive datasets. Cursor pagination filters by the last seen ID/timestamp using an index, staying fast even millions of rows deep, at the trade-off of no arbitrary page-number jumps.

Day 12 Revision Summary

  • Always paginate list endpoints using validated page and limit bounds with a strict maximum cap.
  • Compute skip = (page - 1) * limit and return complete metadata (totalItems, totalPages, currentPage, hasNextPage, hasPrevPage).
  • Allow-list all filter fields and sort options—never pass raw req.query into Model.find().
  • Always append unique _id as a tie-breaker in .sort() for stable, non-duplicating pages.
  • Use Promise.all for data + count queries, add .lean() and indexes, and consider cursor pagination for massive infinite feeds.
