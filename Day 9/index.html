Day 9: File Uploads

Accepting files from users—such as PDF resumes, assignment documents, or profile attachments—introduces entirely new backend challenges. express.json() cannot parse binary file streams, uncapped uploads can fill your server disk or crash RAM in seconds, and trusting a client's original filename or MIME header opens the door to path traversal and malicious uploads. Today you will learn how HTTP multipart/form-data works, how to configure multer upload middleware safely, how to verify real file contents beyond extensions, and when to move from local disk storage to cloud object storage.

Learning Objectives

By the end of Day 9, you will be able to:

  • Explain how binary file uploads travel over HTTP using multipart/form-data boundaries.
  • Describe why dedicated upload middleware (such as multer) is required instead of express.json().
  • Compare local disk storage (diskStorage), temporary staging folders, and memory buffers (memoryStorage).
  • Enforce strict file size limits, file count caps, and allow-listed file types.
  • Verify real file content using magic bytes (file signatures) rather than trusting spoofable extensions or Content-Type headers alone.
  • Generate collision-free, safe filenames that prevent path-traversal attacks (../../).
  • Handle MulterError exceptions cleanly and clean up rejected temporary files.
  • Explain why scalable production apps use dedicated object storage services instead of local container disks.

Prerequisites

Before starting Day 9, make sure you understand:

  • Days 1, 2, 5 & 6 Concepts: Express middleware pipelines, centralized error handling, and server-side validation rules.
  • Node.js Built-In Modules: Familiarity with node:path, node:fs/promises, and node:crypto.
  • Browser vs. Server Boundary: Browser HTML forms or fetch() with FormData send binary bytes over HTTP; Express + Multer on Node.js receive, validate, and store them on the server.

Important Terminology and Definitions

multipart/form-data

An HTTP encoding format that splits a single request body into multiple boundary-separated parts so text fields and raw binary files can travel together without heavy Base64 inflation.

Upload Middleware (multer)

Express middleware that parses incoming multipart/form-data streams, enforces size/type rules, saves files to disk or memory, and attaches req.file / req.files plus text fields on req.body.

Magic Bytes (File Signature)

The first few specific bytes inside a file's binary header (for example, %PDF- or 25 50 44 46 for PDF, or 89 50 4E 47 for PNG) that identify its true format regardless of its filename.

Path Traversal

An attack where a user sends a crafted filename like ../../server.js hoping the server writes files outside the intended uploads folder and overwrites system or app files.

Temporary Staging

Writing an incoming upload into an isolated temp directory first so virus/content checks can inspect it before moving it to permanent storage—or deleting it immediately if invalid.

Object Storage Service

Dedicated cloud storage (such as Amazon S3, Cloudflare R2, or Google Cloud Storage) designed to store files durably outside ephemeral app servers and serve them via CDNs or signed URLs.

Detailed Theory and Explanations

1. How File Uploads Work Over HTTP (multipart/form-data)

When a browser submits a file using <input type="file"> inside a form or via JavaScript new FormData(), it sets the header Content-Type: multipart/form-data; boundary=----WebKitFormBoundary.... Each field (text or binary file) is wrapped inside boundary markers along with a Content-Disposition header and a browser-guessed Content-Type.

Express's built-in express.json() only understands application/json text and completely ignores multipart/form-data. That is why you need dedicated multipart streaming middleware like multer (built on busboy) to parse chunks incrementally without freezing the Node.js event loop.

2. Temporary Storage, Local Disk, and Memory Buffers

Storage Strategy How It Works Best Use Case & Trade-Off
Local Disk (diskStorage) Streams incoming chunks directly into a folder on the server's hard drive. Low RAM usage; great for single-server apps or temporary staging before magic-byte inspection or cloud upload.
Memory Buffer (memoryStorage) Holds the entire uploaded file as a Buffer inside Node.js RAM (req.file.buffer). Fast for tiny files (e.g., under 2 MB) sent straight to image resizing or S3—but dangerous if large files or concurrent uploads exhaust RAM!
Cloud Object Storage Backend (or browser via presigned URL) stores files in S3 / R2 / GCS instead of app servers. Essential for production horizontal scaling and ephemeral hosts (Render/Heroku/containers) whose local files vanish on redeploy.

3. File Size Limits, Type Validation, and Content Checking

Never allow unlimited uploads. Always configure explicit caps inside multer({ limits: { fileSize: ..., files: ... } }) so oversized streams abort early before filling your disk or RAM.

Equally important: never trust file.originalname or file.mimetype by themselves! Any attacker using curl can rename an executable script malware.exe to resume.pdf and manually set Content-Type: application/pdf. Effective upload validation uses a three-step funnel:

  1. Pre-filter in fileFilter: Check extension and declared MIME type against a strict allow-list (never a deny-list) to reject obvious mismatches before writing bytes.
  2. Verify real content (Magic Bytes): After receiving the file buffer or temporary file, inspect the leading binary bytes (signature) on the server to confirm the bytes actually match a PDF, PNG, JPEG, or plain UTF-8 text file.
  3. Delete rejected files immediately: If magic-byte inspection fails after staging to a temp folder, unlink (delete) the temporary file in a finally or catch block so junk does not accumulate on disk.

4. Safe File Naming & Preventing Unsafe Uploads

Never save an uploaded file using req.file.originalname. A user could submit ../../.env (path traversal) or overwrite another user's report.pdf, or upload payload.html / evil.svg containing embedded JavaScript that executes (Stored XSS) if served directly from your website's origin!

Follow these non-negotiable naming and serving rules:

  • Generate a fresh random filename using crypto.randomUUID() plus a server-controlled extension derived from your verified allow-list (never directly from user input).
  • Store uploads in a private directory outside your public static web root, or serve downloadable documents with Content-Disposition: attachment and X-Content-Type-Options: nosniff so browsers download them safely instead of executing them inline.
  • Keep original user-friendly filenames only as sanitized metadata in MongoDB, never as the physical path on disk.

5. Upload Error Handling

When an upload violates a Multer limit, Multer passes a MulterError instance (with codes like LIMIT_FILE_SIZE, LIMIT_FILE_COUNT, or LIMIT_UNEXPECTED_FILE) into Express's next(err) error pipeline. Normalizing MulterError inside your centralized error handler lets your API return clean 400 or 413 Payload Too Large JSON responses instead of ugly stack traces.

Step 2: Create a Magic-Byte Content Inspector Utility (src/utils/fileSignature.js)

This pure Node.js helper reads only the first 8 bytes of a staged file and verifies whether its binary signature truly matches PNG, JPEG, or PDF.

Backend Source Code: src/utils/fileSignature.js (Runs on Node.js)

import fs from 'node:fs/promises';

const SIGNATURES = [
  {
    type: 'pdf',
    mime: 'application/pdf',
    ext: '.pdf',
    matches: (buf) => buf.length >= 4 && buf.subarray(0, 4).toString('ascii') === '%PDF'
  },
  {
    type: 'png',
    mime: 'image/png',
    ext: '.png',
    matches: (buf) =>
      buf.length >= 8 &&
      buf[0] === 0x89 &&
      buf[1] === 0x50 &&
      buf[2] === 0x4e &&
      buf[3] === 0x47 &&
      buf[4] === 0x0d &&
      buf[5] === 0x0a &&
      buf[6] === 0x1a &&
      buf[7] === 0x0a
  },
  {
    type: 'jpeg',
    mime: 'image/jpeg',
    ext: '.jpg',
    matches: (buf) =>
      buf.length >= 3 &&
      buf[0] === 0xff &&
      buf[1] === 0xd8 &&
      buf[2] === 0xff
  }
];

export const detectVerifiedFileType = async (filePath) => {
  const handle = await fs.open(filePath, 'r');
  try {
    const buffer = Buffer.alloc(8);
    const { bytesRead } = await handle.read(buffer, 0, 8, 0);
    const slice = buffer.subarray(0, bytesRead);

    for (const sig of SIGNATURES) {
      if (sig.matches(slice)) {
        return { mime: sig.mime, ext: sig.ext, type: sig.type };
      }
    }
    return null;
  } finally {
    await handle.close();
  }
};

Step 3: Configure Multer Upload Middleware with Safe Staging & Limits (src/middleware/uploadMiddleware.js)

Notice that we resolve paths safely inside storage/tmp, never trust originalname on disk, and enforce strict fileSize and files caps.

Backend Source Code: src/middleware/uploadMiddleware.js (Runs on Node.js)

import fs from 'node:fs';
import path from 'node:path';
import crypto from 'node:crypto';
import multer from 'multer';

export const TMP_UPLOAD_DIR = path.resolve(process.cwd(), 'storage', 'tmp');
export const SAFE_UPLOAD_DIR = path.resolve(process.cwd(), 'storage', 'uploads');

fs.mkdirSync(TMP_UPLOAD_DIR, { recursive: true });
fs.mkdirSync(SAFE_UPLOAD_DIR, { recursive: true });

const ALLOWED_MIME_TO_EXT = new Map([
  ['application/pdf', '.pdf'],
  ['image/png', '.png'],
  ['image/jpeg', '.jpg']
]);

const storage = multer.diskStorage({
  destination: (req, file, cb) => {
    cb(null, TMP_UPLOAD_DIR);
  },
  filename: (req, file, cb) => {
    const ext = ALLOWED_MIME_TO_EXT.get(file.mimetype) || '';
    const safeName = `${crypto.randomUUID()}${ext}`;
    cb(null, safeName);
  }
});

const fileFilter = (req, file, cb) => {
  if (!ALLOWED_MIME_TO_EXT.has(file.mimetype)) {
    const err = new Error('Only PDF, PNG, and JPEG files are allowed.');
    err.statusCode = 400;
    return cb(err);
  }
  return cb(null, true);
};

export const uploadSingleDocument = multer({
  storage,
  fileFilter,
  limits: {
    fileSize: 2 * 1024 * 1024,
    files: 1
  }
}).single('document');

Step 4: Build the Controller with Content Inspection, Cleanup & Safe Download

Backend Source Code: src/controllers/uploadController.js (Runs on Node.js) 

import fs from 'node:fs/promises';
import path from 'node:path';
import crypto from 'node:crypto';
import { detectVerifiedFileType } from '../utils/fileSignature.js';
import { SAFE_UPLOAD_DIR } from '../middleware/uploadMiddleware.js';

const safeUnlink = async (targetPath) => {
  if (!targetPath) return;
  try {
    await fs.unlink(targetPath);
  } catch (err) {
    if (err.code !== 'ENOENT') {
      console.error('Failed to clean temp file:', err.message);
    }
  }
};

export const handleDocumentUpload = async (req, res, next) => {
  if (!req.file) {
    return res.status(400).json({
      status: 'fail',
      message: 'Please attach a file under the field name "document".'
    });
  }

  const tempPath = req.file.path;

  try {
    const verified = await detectVerifiedFileType(tempPath);

    if (!verified || verified.mime !== req.file.mimetype) {
      await safeUnlink(tempPath);
      return res.status(400).json({
        status: 'fail',
        message: 'File content does not match a valid PDF, PNG, or JPEG signature.'
      });
    }

    const storedFilename = `${crypto.randomUUID()}${verified.ext}`;
    const finalPath = path.join(SAFE_UPLOAD_DIR, storedFilename);
    await fs.rename(tempPath, finalPath);

    return res.status(201).json({
      status: 'success',
      data: {
        fileId: storedFilename,
        originalName: path.basename(req.file.originalname).slice(0, 100),
        verifiedMime: verified.mime,
        sizeBytes: req.file.size
      }
    });
  } catch (err) {
    await safeUnlink(tempPath);
    return next(err);
  }
};

export const downloadDocument = async (req, res) => {
  const { fileId } = req.params;

  if (!/^[0-9a-f-]{36}\.(pdf|png|jpg)$/.test(fileId)) {
    return res.status(400).json({ status: 'fail', message: 'Invalid file identifier.' });
  }

  const resolvedPath = path.resolve(SAFE_UPLOAD_DIR, fileId);
  if (!resolvedPath.startsWith(SAFE_UPLOAD_DIR + path.sep)) {
    return res.status(403).json({ status: 'fail', message: 'Access denied.' });
  }

  try {
    await fs.access(resolvedPath);
    res.setHeader('X-Content-Type-Options', 'nosniff');
    return res.download(resolvedPath, fileId);
  } catch {
    return res.status(404).json({ status: 'fail', message: 'File not found.' });
  }
};

Step 5: Mount Routes and Normalize MulterError in src/app.js

Backend Source Code: src/app.js (Runs on Node.js)

import express from 'express';
import multer from 'multer';
import { uploadSingleDocument } from './middleware/uploadMiddleware.js';
import { handleDocumentUpload, downloadDocument } from './controllers/uploadController.js';

const app = express();
app.disable('x-powered-by');

app.post('/api/v1/uploads', uploadSingleDocument, handleDocumentUpload);
app.get('/api/v1/uploads/:fileId', downloadDocument);

app.use((err, req, res, next) => {
  if (err instanceof multer.MulterError) {
    const statusCode = err.code === 'LIMIT_FILE_SIZE' ? 413 : 400;
    const message =
      err.code === 'LIMIT_FILE_SIZE'
        ? 'Uploaded file exceeds the 2 MB limit.'
        : `Upload error: ${err.message}`;

    return res.status(statusCode).json({
      status: 'fail',
      errorCode: err.code,
      message
    });
  }

  return res.status(err.statusCode || 500).json({
    status: err.statusCode && err.statusCode < 500 ? 'fail' : 'error',
    message: err.message || 'Upload processing failed.'
  });
});

app.listen(5000, () => {
  console.log('Upload server listening on port 5000');
});

Step 6: Browser-Side Upload vs. Terminal curl Upload Test

Remember: browser JavaScript creates a FormData object and lets the browser set the multipart boundary header automatically (never manually set Content-Type: multipart/form-data in fetch headers!).

Browser-Side JavaScript Example (Runs in Browser)

async function uploadSampleFile(fileInputElement) {
  const file = fileInputElement.files[0];
  const formData = new FormData();
  formData.append('document', file);

  const response = await fetch('http://localhost:5000/api/v1/uploads', {
    method: 'POST',
    body: formData
  });

  const result = await response.json();
  console.log(result);
}

curl -X POST http://localhost:5000/api/v1/uploads \
  -F "document=@./sample-brochure.pdf"

Real-World Use Cases

1. Job Portal Resume Uploads

A careers portal limits applicants to 2 MB PDF resumes, checks the %PDF binary signature on the server, renames files to UUIDs, and serves them with Content-Disposition: attachment to HR reviewers.

2. Student Assignment Submissions

Universities enforce strict file count limits, record ownership and submission timestamps in MongoDB, and store files in S3-compatible object storage so multiple backend instances can access them.

3. Support Ticket Diagnostic Attachments

Helpdesk APIs inspect PNG/JPEG/log attachments in a temporary staging folder before pushing safe uploads to private cloud buckets and issuing short-lived signed download URLs.

4. Direct-to-Cloud Presigned Uploads

For very large videos (100 MB+), Express generates a short-lived presigned S3/R2 upload URL so the browser streams bytes straight to cloud storage without tying up Node.js bandwidth or memory.

Common Mistakes, Security Notes, and Best Practices

Common File-Upload Mistakes

  • Manually setting Content-Type: multipart/form-data in browser fetch(): Doing so omits the required boundary=... string and breaks server parsing! Let the browser set the header automatically when passing FormData.
  • Using req.file.originalname as the disk filename: Risks path traversal (../../), overwriting existing user files, and special-character filesystem errors.
  • Using memoryStorage() for large files: Ten users uploading 50 MB files concurrently consumes 500 MB of Node.js RAM and crashes the process.
  • Leaving orphaned files in tmp/: Forgetting to unlink staged files when validation or database writes fail slowly fills up server disk space.
  • Relying on local disk in ephemeral containers: Cloud platforms like Render/Fly/Heroku wipe container disks on every deploy—use persistent volumes or cloud object storage in production.

Security & Best-Practice Notes

  • Verify magic bytes, not just extensions: Check actual binary header signatures on the server to detect spoofed files.
  • Avoid serving untrusted HTML or SVG inline: SVG files can embed <script> tags! Serve user uploads as attachments (res.download), from a separate asset domain, or sanitize/re-encode images (covered on Day 10).
  • Prevent path traversal on downloads: Validate file IDs strictly with regex and verify resolvedPath.startsWith(SAFE_UPLOAD_DIR + path.sep).
  • Store uploads outside public static directories: Keep raw user files out of public/ so authentication and ownership checks run before every download.

Short-Answer Questions

Think through each answer carefully before opening the explanation.

1. Why does multipart/form-data work better than Base64-encoded JSON for uploading larger files?

Base64 encoding expands binary file sizes by roughly 33% and forces express.json() to buffer and parse huge strings in memory. multipart/form-data streams raw binary bytes incrementally with minimal overhead.

2. Explain the two-stage validation approach combining Multer's fileFilter and magic-byte inspection.

fileFilter checks the declared MIME type/extension early to reject blatantly invalid uploads before writing to disk. Then magic-byte inspection reads the actual leading binary bytes of the uploaded file to confirm the real file content wasn't spoofed.

3. Why should temporary staged files always be unlinked inside catch/error paths?

If an upload fails content verification or database persistence after being written to storage/tmp/, leaving it behind leaks disk space over time and keeps unverified files on your server.

4. How do UUID filenames protect against both path traversal and overwrite bugs?

Generating a fresh server-side crypto.randomUUID() + verified extension completely ignores user-supplied path segments (like ../../) and guarantees two users uploading files named resume.pdf never overwrite each other.

5. When should a team move from local disk uploads to cloud object storage like S3 or Cloudflare R2?

As soon as the application deploys to ephemeral containers, runs multiple backend instances behind a load balancer, or serves high-traffic media that benefits from CDN distribution and durable external backups.

Day 9 Revision Summary

  • File uploads travel over HTTP as multipart/form-data and require streaming middleware like multer.
  • Always set explicit limits (fileSize, files) and handle MulterError cleanly in centralized error middleware.
  • Never trust originalname or declared MIME headers alone—generate UUID filenames and verify real file signatures (magic bytes).
  • Clean up staged temp files on rejection, store uploads outside public web roots, and serve downloads with nosniff / Content-Disposition.
  • For multi-server or ephemeral cloud deployments, migrate storage to dedicated cloud object storage (S3, R2, GCS).
