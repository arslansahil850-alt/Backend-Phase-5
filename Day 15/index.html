Day 15: Performance Optimization

An API that feels instant with 1 user and 20 test documents can crawl to 3-second response times—or crash entirely—when 500 concurrent users query 200,000 records. Real performance engineering is never guesswork: you measure first, locate the actual bottleneck (slow database scans, N+1 query loops, bloated JSON payloads, or blocked Node.js event loops), apply targeted fixes with clear trade-offs, and verify measurable gains safely. Today you will master database indexing, query optimization, payload compression, caching with safe invalidation, background jobs, and safe load-testing workflows.

Learning Objectives

By the end of Day 15, you will be able to:

  • Define core backend performance metrics: latency (average vs. p95/p99), throughput (requests/sec), and resource utilization.
  • Follow the golden rule of optimization: measure before optimizing using timing logs and MongoDB .explain('executionStats').
  • Eliminate N+1 query loops, fetch only needed fields via .select(), and skip document hydration via .lean().
  • Design effective MongoDB compound indexes and explain their write-speed and memory trade-offs.
  • Shrink network payloads with field projection and HTTP compression middleware.
  • Implement cache-aside caching with TTL expiration and explicit cache invalidation on writes.
  • Keep Node.js's single-threaded event loop responsive by offloading slow tasks asynchronously and avoiding synchronous I/O.
  • Run safe, controlled load tests strictly against isolated local or staging environments.

Prerequisites

Before starting Day 15, make sure you understand:

  • Days 1–14 Concepts: Express middleware pipelines, request timing loggers, MongoDB/Mongoose queries, pagination, and search indexes.
  • Node.js Event Loop Basics: Knowing that Node.js runs JavaScript on one main thread; synchronous CPU loops or fs.readFileSync() block every incoming HTTP request!

Important Terminology and Definitions

Latency & p95 / p99

Latency is how long one request takes (in ms). p95 means 95% of requests finish faster than that threshold—catching slow tail requests that averages hide.

Throughput (RPS)

Requests per second (RPS) your backend can serve sustainably without spiking errors or exhausting CPU/database connections.

N+1 Query Problem

Fetching a list of N parent records in 1 query, then running N separate database queries inside a loop to fetch related data for each item.

Collection Scan (COLLSCAN)

When MongoDB lacks a matching index and must read every single document in the collection from start to finish, rather than jumping straight via an index (IXSCAN).

Cache-Aside & Invalidation

Checking a fast cache before querying MongoDB; storing the result with a Time-To-Live (TTL); and deleting/updating that cache key whenever underlying data changes.

Background Job

Slow non-critical work (sending welcome emails, generating PDF invoices, syncing search) queued to run asynchronously outside the user's immediate HTTP response.

Detailed Theory and Explanations

1. Measuring Before Optimizing

Guessing where an API is slow often wastes hours tuning a 1 ms function while ignoring a 400 ms unindexed database scan. Always collect baseline measurements first:

  • Route Timing Logs: Use your Day 2 requestLogger (with process.hrtime.bigint()) to surface slow endpoints.
  • Database Query Plans: Inspect MongoDB's await Model.find(filter).explain('executionStats') in dev to check executionTimeMillis, totalDocsExamined vs. nReturned, and whether MongoDB used IXSCAN instead of COLLSCAN.
  • Process Health: Monitor Node.js heap memory (process.memoryUsage()) and event-loop responsiveness.

2. Efficient Database Queries & Index Trade-Offs

Three low-effort Mongoose habits deliver massive speedups immediately:

  • Fix N+1 Queries: Never put await Order.find({ userId }) inside a for (const user of users) loop! Collect all IDs first and run a single batch query using { userId: { $in: userIds } } or an aggregation pipeline.
  • Project Only Needed Fields: Calling .select('title category price') avoids transferring massive description paragraphs or arrays when rendering summary cards.
  • Use .lean() on Read Queries: Plain objects skip Mongoose change-tracking wrappers and serialize to JSON much faster.

Database Indexes & Their Trade-Offs: Indexes turn linear scans into fast tree lookups. Follow the ESR rule when building compound indexes: Equality fields first, Sort fields second, Range fields last (e.g., { category: 1, createdAt: -1, price: 1 }). However, indexes are not free—every additional index consumes RAM/disk and slightly slows down INSERT, UPDATE, and DELETE operations because MongoDB must update every index on write. Index only queries that actually run frequently!

3. Response Payload Optimization & Compression

Sending smaller HTTP responses saves both server serialization CPU and user mobile bandwidth. First, trim unused JSON properties with DTOs/projections and paginate lists. Second, register Express's compression() middleware to gzip/Brotli-compress text and JSON responses over ~1 KB—often shrinking JSON payloads by 70–85%.

Note: Do not waste CPU re-compressing already-compressed formats like WebP, JPEG, PNG, or ZIP files (compression skips common binary MIME types by default).

4. Caching Fundamentals & Cache Invalidation

If 1,000 visitors load GET /api/v1/projects/featured every minute and featured projects change only a few times a day, querying MongoDB 1,000 times is wasteful. With the cache-aside pattern:

  1. Check fast cache (in-memory TTL cache for single-instance apps, or shared Redis for multi-instance apps).
  2. On a cache hit, return the cached JSON immediately (often < 2 ms).
  3. On a cache miss, query MongoDB, store the response in cache with a bounded TTL (e.g., 60 seconds), and return it.
  4. Cache Invalidation: Whenever an admin creates, updates, or deletes a featured project, explicitly delete (invalidate) the affected cache key so users do not see stale data!

Critical Safety Rule: Never cache private user-specific responses under a shared global key—always include userId in private cache keys or cache only public shared data!

5. Asynchronous Work & Background Jobs

Never block the Node.js event loop with synchronous calls like fs.readFileSync(), bcrypt.hashSync(), or giant nested for loops inside request handlers. Additionally, when a user signs up or submits an order, avoid forcing the HTTP response to wait 2 seconds for external SMTP email servers or PDF generators when possible—enqueue background jobs (using a job queue like BullMQ + Redis in production, or non-blocking async task workers) so the HTTP endpoint responds rapidly.

6. Safe Load Testing Concepts

Tools such as autocannon, k6, or ApacheBench measure how many requests/second and what p95 latency your API achieves under concurrent traffic. Golden safety rule: run load tests strictly against your local machine or a dedicated staging environment—never against production databases or third-party servers! Disable or whitelist test runners carefully when testing behind rate limiters so you measure real application throughput accurately.

Step-by-Step Tutorial: Inspecting & Optimizing a Slow API

Let us examine a slow Express + Mongoose dashboard endpoint with classic bottlenecks (N+1 loop, missing projection/lean, sequential awaits, no compression, no cache) and optimize it step by step on Node.js (server-side).

Unoptimized Backend Code (Causes N+1 DB Calls & Heavy Payloads)

    const authors = await Author.find();

Step 2: Build a Safe Bounded TTL Cache Utility (src/utils/ttlCache.js)

A clean Map-based cache with both per-entry TTL expiration and a maxEntries cap so memory never grows unboundedly in single-instance apps (swap for Redis when scaling across multiple servers).

Backend Source Code: src/utils/ttlCache.js (Runs on Node.js)

export class TtlCache {
  constructor({ defaultTtlMs = 60_000, maxEntries = 500 } = {}) {
    this.defaultTtlMs = defaultTtlMs;
    this.maxEntries = maxEntries;
    this.store = new Map();
  }

  get(key) {
    const entry = this.store.get(key);
    if (!entry) {
      return null;
    }

    if (Date.now() > entry.expiresAt) {
      this.store.delete(key);
      return null;
    }

    return entry.value;
  }

  set(key, value, ttlMs = this.defaultTtlMs) {
    if (this.store.size >= this.maxEntries && !this.store.has(key)) {
      const oldestKey = this.store.keys().next().value;
      if (oldestKey !== undefined) {
        this.store.delete(oldestKey);
      }
    }

    this.store.set(key, {
      value,
      expiresAt: Date.now() + ttlMs
    });
  }

  invalidate(key) {
    this.store.delete(key);
  }

  invalidatePrefix(prefix) {
    for (const key of this.store.keys()) {
      if (key.startsWith(prefix)) {
        this.store.delete(key);
      }
    }
  }
}

Step 3: Optimize the Service with Batching, .lean(), Projection & Cache-Aside

Notice how 101 queries drop to just 2 fast indexed queries (or 0 queries on cache hit), and creating/updating a book invalidates the cached summary immediately.

Backend Source Code: src/services/dashboardService.js (Runs on Node.js)

import Author from '../models/Author.js';
import Book from '../models/Book.js';
import { TtlCache } from '../utils/ttlCache.js';

const dashboardCache = new TtlCache({ defaultTtlMs: 30_000, maxEntries: 100 });

export const getAuthorsSummaryOptimized = async ({ page = 1, limit = 20 }) => {
  const cacheKey = `authors:summary:p${page}:l${limit}`;
  const cached = dashboardCache.get(cacheKey);

  if (cached) {
    return { fromCache: true, ...cached };
  }

  const skip = (page - 1) * limit;

  const [authors, totalAuthors] = await Promise.all([
    Author.find()
      .select('name bio')
      .sort({ name: 1, _id: 1 })
      .skip(skip)
      .limit(limit)
      .lean(),
    Author.countDocuments()
  ]);

  const authorIds = authors.map((a) => a._id);

  const books = authorIds.length > 0
    ? await Book.find({ authorId: { $in: authorIds } })
        .select('title publishedYear authorId')
        .lean()
    : [];

  const booksByAuthor = new Map();
  for (const book of books) {
    const key = String(book.authorId);
    if (!booksByAuthor.has(key)) {
      booksByAuthor.set(key, []);
    }
    booksByAuthor.get(key).push({
      id: book._id,
      title: book.title,
      publishedYear: book.publishedYear
    });
  }

  const data = authors.map((author) => {
    const authorBooks = booksByAuthor.get(String(author._id)) || [];
    return {
      id: author._id,
      name: author.name,
      bookCount: authorBooks.length,
      books: authorBooks
    };
  });

  const payload = {
    pagination: {
      totalItems: totalAuthors,
      totalPages: Math.ceil(totalAuthors / limit),
      currentPage: page,
      limit
    },
    data
  };

  dashboardCache.set(cacheKey, payload);
  return { fromCache: false, ...payload };
};

export const invalidateAuthorSummaries = () => {
  dashboardCache.invalidatePrefix('authors:summary:');
};

Step 4: Enable Compression & Slow-Request Monitoring in src/app.js

Backend Source Code: src/app.js (Runs on Node.js)

import express from 'express';
import compression from 'compression';
import { getAuthorsSummaryOptimized, invalidateAuthorSummaries } from './services/dashboardService.js';

const app = express();
app.disable('x-powered-by');
app.use(compression({ threshold: 1024 }));
app.use(express.json({ limit: '10kb' }));

app.use((req, res, next) => {
  const startNs = process.hrtime.bigint();
  res.on('finish', () => {
    const ms = Number(process.hrtime.bigint() - startNs) / 1_000_000;
    if (ms > 250) {
      console.warn(`[SLOW REQUEST] ${req.method} ${req.originalUrl} -> ${res.statusCode} (${ms.toFixed(1)} ms)`);
    }
  });
  next();
});

app.get('/api/v1/dashboard/authors', async (req, res, next) => {
  try {
    const page = Math.max(1, Number(req.query.page) || 1);
    const limit = Math.min(50, Math.max(1, Number(req.query.limit) || 20));
    const result = await getAuthorsSummaryOptimized({ page, limit });

    res.setHeader('X-Cache', result.fromCache ? 'HIT' : 'MISS');
    return res.status(200).json({
      status: 'success',
      pagination: result.pagination,
      data: result.data
    });
  } catch (err) {
    return next(err);
  }
});

app.post('/api/v1/books', async (req, res) => {
  invalidateAuthorSummaries();
  res.status(201).json({ status: 'success', message: 'Book saved and summary cache invalidated.' });
});

export default app;

Real-World Use Cases

1. Fixing N+1 Bottlenecks on Feeds

Replacing a loop of per-post Comment.countDocuments() calls with one MongoDB aggregation or batched $in query routinely cuts API latency from 800 ms down to 15 ms.

2. Caching Public Catalog & Config Data

Homepages, category navigation trees, and exchange rates rarely change every second; caching them in Redis for 60 seconds slashes database CPU load by 95%+.

3. Gzip/Brotli Compression for Mobile APIs

Compressing a 120 KB paginated JSON product response down to ~18 KB dramatically speeds up loading over slower 3G/4G mobile connections.

4. Offloading Heavy Exports & Emails

Instead of making a user wait 8 seconds while Node.js generates a multi-page PDF report and emails it via Nodemailer, enqueue a background job and return 202 Accepted immediately.

Common Mistakes, Security Notes, and Best Practices

Common Performance Mistakes

  • Optimizing blindly without measuring: Adding caches or complex code before profiling wastes time and adds bugs while missing the actual bottleneck.
  • Using synchronous Node.js APIs in routes: Calling fs.readFileSync, bcrypt.hashSync, or heavy JSON loops stalls the entire Node event loop for every active user.
  • Unbounded in-memory caches: Storing keys in a plain JavaScript object without TTL expiration or maxEntries causes a slow memory leak until Node.js crashes!
  • Over-indexing every field in MongoDB: Slows down writes and wastes valuable RAM needed for hot working-set indexes.
  • Running load tests against production or external sites: Can cause a real outage or look like a DoS attack. Test strictly on local or isolated staging!

Security & Best-Practice Notes

  • Never share private cached responses across users: Always namespace private caches by userId, or restrict caching strictly to public non-sensitive endpoints.
  • Always invalidate or expire caches: Combine explicit invalidation on writes with a reasonable TTL safety net so stale permissions or prices never linger indefinitely.
  • Check explain('executionStats') on critical queries: Verify IXSCAN is used and totalDocsExamined stays close to nReturned.
  • Keep logs lightweight & safe: Log slow-request metrics without dumping sensitive payloads or headers.

Hands-On Exercises

  1. Measure X-Cache: MISS vs. HIT: Send two consecutive curl -i http://localhost:5000/api/v1/dashboard/authors requests and compare response headers and timing logs.
  2. Compression Size Check: Send a request with curl -H "Accept-Encoding: gzip" -i ... vs. without it and observe the Content-Encoding: gzip header and smaller transferred byte count.
  3. Inspect a MongoDB Query Plan: In a small local Node script or mongosh, run .explain('executionStats') on a query both before and after adding a compound index, comparing COLLSCAN vs. IXSCAN and totalDocsExamined.
  4. Cache Invalidation Verification: Trigger POST /api/v1/books, then immediately re-request the dashboard endpoint and verify X-Cache: MISS confirms stale data was cleared.

Short-Answer Questions

Think through each answer carefully before opening the explanation.

1. Why is looking only at average latency misleading compared to also checking p95 or p99 latency?

Averages hide painful outliers. An endpoint might average 40 ms while the slowest 5% of users (p95) wait 1,800 ms due to unindexed queries or garbage-collection pauses.

2. Explain how to fix an N+1 query loop in Mongoose.

Instead of querying inside a loop per parent record, collect all parent IDs into an array and execute a single batched Model.find({ parentId: { $in: ids } }).lean() query (or MongoDB aggregation), then group results in a JavaScript Map.

3. Explain the ESR rule for designing compound MongoDB indexes.

Order compound index keys as Equality filters first, Sort fields second, and Range filters last so MongoDB narrows exact matches, reads results already sorted, and scans minimal index keys.

4. Why do slow tasks like sending bulk emails or generating PDFs belong in asynchronous background jobs?

Keeping multi-second third-party network calls or CPU-heavy generation inside HTTP handlers creates terrible user wait times and risks request timeouts. Queuing jobs lets the API respond immediately while workers process tasks reliably.

5. What trade-offs exist between adding a cache and querying the database directly?

Caching dramatically improves read latency and lowers database load, at the trade-off of extra infrastructure/memory complexity and the risk of temporarily stale data if cache invalidation is missed.

Day 15 Revision Summary

  • Always measure baseline latency, p95/p99, and explain('executionStats') before optimizing.
  • Eliminate N+1 loops with batched $in queries, project only required fields, use .lean(), and run independent awaits via Promise.all.
  • Design compound indexes using the ESR rule while respecting write/memory trade-offs.
  • Shrink payloads with compression(), use bounded cache-aside caching with proper invalidation, keep the Node event loop non-blocking, and load-test strictly in safe local/staging environments.
