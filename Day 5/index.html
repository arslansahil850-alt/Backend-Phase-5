Day 5: Advanced Error Handling

In a beginner Express app, errors are handled ad hoc with scattered try/catch blocks returning inconsistent JSON shapes—or worse, crashing the entire Node.js server or leaking sensitive stack traces to users. Production APIs treat error handling as a first-class architectural layer. Today you will learn the difference between operational and programming errors, how to build custom error classes, how to normalize Mongoose and JSON errors, and how to design a centralized error-handling pipeline that keeps both users and servers safe.

Learning Objectives

By the end of Day 5, you will be able to:

  • Distinguish clearly between operational errors and programming errors.
  • Explain how synchronous and asynchronous errors propagate through Express middleware.
  • Design custom error classes (such as AppError) carrying HTTP status codes, error codes, and isOperational flags.
  • Build a centralized 4-argument Express error-handling middleware (err, req, res, next).
  • Normalize Mongoose validation errors, malformed ObjectId CastErrors, duplicate key 11000 errors, and malformed JSON syntax errors into clean API responses.
  • Select accurate HTTP status codes (400, 401, 403, 404, 409, 422, 500).
  • Return rich debugging details in development while preventing information leakage in production.
  • Log server errors safely and configure process-level safety handlers for unhandledRejection and uncaughtException.

Prerequisites

Before starting Day 5, ensure you understand:

  • Days 1–4 Concepts: Express middleware order, next(err), asyncHandler, and layered project structure (utils/, middleware/, services/, controllers/).
  • JavaScript Classes & Inheritance: Extending the built-in Error class using class AppError extends Error and super(message).
  • Environment Separation: Reading env.isProduction vs. development mode from src/config/env.js.

Important Terminology and Definitions

Operational Error

A predictable, runtime failure caused by external inputs or environment conditions—such as invalid user input, a missing record (404), duplicate email, or database timeout.

Programming Error

An unexpected bug in source code—such as reading a property of undefined, a typo in a variable name, or passing wrong argument types.

Centralized Error Middleware

A single 4-parameter Express middleware (err, req, res, next) placed at the bottom of app.js that catches all forwarded errors and formats consistent responses.

Custom Error Class (AppError)

A subclass of JavaScript's built-in Error that attaches HTTP metadata like statusCode, errorCode, details, and isOperational: true.

Information Leakage

Accidentally exposing stack traces, server file paths, database driver messages, or library versions in API responses—giving attackers clues about your backend internals.

unhandledRejection

A Node.js process event emitted whenever an asynchronous Promise rejects without a .catch() handler anywhere in the call stack.

Detailed Theory and Explanations

1. Operational vs. Programming Errors

Not all errors deserve the same response. Distinguishing between operational and programming errors is the foundation of reliable backend engineering:

Aspect Operational Errors Programming Errors
Cause Invalid client input, expired token, record not found, duplicate key, network timeout Developer bug (e.g., TypeError: Cannot read properties of undefined)
Predictable? Yes—expected during normal system operation No—unintended defect that requires a code fix
Client Response (Prod) Clear, helpful 4xx message (e.g., "Email is already registered.") Generic 500 message ("Something went wrong on our end.")
Server Action Log cleanly at warn/info level; keep server running normally Log full stack trace privately; alert engineers; restart cleanly if process state is corrupted

2. Synchronous vs. Asynchronous Errors in Express

When a synchronous route handler executes throw new AppError('Invalid filter', 400), Express catches that thrown exception automatically and forwards it to the 4-argument error middleware.

However, when an asynchronous controller uses async/await in Express 4, an awaited rejection turns into a rejected Promise. Express 4 does not await the return value of handlers, so an uncaught rejection inside an async function bypasses Express error middleware completely unless wrapped in try/catch + next(err) or our asyncHandler utility. Even in Express 5 (which adds native async promise catching), keeping explicit error utilities and consistent next(err) patterns keeps services and middleware predictable.

3. Custom Error Classes & Consistent API Error Responses

Throwing plain strings or generic new Error('Not found') forces your error handler to guess what HTTP status code applies. By extending Error with an AppError class, services and controllers can throw rich, structured errors:

  • statusCode: The exact HTTP code (400, 404, 409, etc.).
  • status: Derived automatically—'fail' for 4xx client errors and 'error' for 5xx server errors.
  • errorCode: A machine-readable string like 'DUPLICATE_RESOURCE' or 'VALIDATION_ERROR' so frontend apps can localize or react cleanly.
  • isOperational: Set to true so the centralized handler knows the error message is safe to display to the client in production.

Every error response returned by your API should follow one predictable JSON envelope—for example: { status, errorCode, message, requestId, details? }.

4. Choosing Accurate HTTP Status Codes

Status Code Meaning When to Use in an API
400 Bad Request Malformed request or invalid input syntax Broken JSON body, invalid MongoDB ObjectId format, missing required fields
401 Unauthorized Missing or invalid authentication credentials Missing Bearer token, expired or invalid token
403 Forbidden Authenticated, but lacks permission Member role attempting an admin-only action
404 Not Found Requested route or resource does not exist Unknown URL path or valid ID with no matching document
409 Conflict Request conflicts with current resource state Duplicate unique email/slug, or booking when capacity is full
422 Unprocessable Entity Syntactically valid JSON, semantic rule violation End date earlier than start date, or schema field validation errors
500 Internal Server Error Unexpected server-side bug or failure Programming errors or unhandled internal failures

5. Handling Validation, JSON Parsing, and Database Errors

Many common errors originate from Express built-in parsers or Mongoose rather than your custom throw new AppError(...) statements. Inside your centralized error middleware, translate those library-specific errors into clean operational AppError instances:

  • Malformed JSON (SyntaxError with err.type === 'entity.parse.failed'): Thrown by express.json() when a client sends broken JSON like {"name": }. Map to 400 Bad Request.
  • Mongoose CastError: Occurs when an invalid string (e.g., "abc") is queried as an ObjectId. Map to 400 Bad Request.
  • Mongoose ValidationError: Occurs when schema rules (required, min, enum) fail. Extract field messages into a clean 400 or 422 response with structured details.
  • MongoDB Duplicate Key (err.code === 11000): Occurs when inserting a duplicate value into a unique: true index. Map to 409 Conflict without exposing raw index names.

6. Safe Logging & Avoiding Information Leakage

In development, developers need the full error object and err.stack to debug fast. In production, returning err.stack, file paths (like /var/www/app/src/services/userService.js:42), or raw MongoDB index strings leaks internal architecture to potential attackers.

Always separate what you log on the server (timestamp, requestId, method, URL, status code, sanitized message, stack trace for 5xx) from what you send to the client (safe operational message or generic 500 fallback in production).

Diagram: Centralized Error-Handling Flow

Trace how errors from any layer—parsers, middleware, controllers, services, or Mongoose—converge into one centralized pipeline:

1. Error Sources Controllers / Services / Mongoose / express.json() / 404 Handler Throws AppError, Mongoose error, or calls next(err) via asyncHandler
↓
2. Error Normalization Centralized Error Middleware (err, req, res, next) Maps CastError → 400, ValidationError → 422, Duplicate 11000 → 409, Bad JSON → 400
↓
3a. Development Mode Full Diagnostics Logs full error + returns message, errorCode, details, and stack
3b. Production Mode Leak-Free Safe Response If isOperational: sends safe message; if programming bug: logs privately & sends generic 500

Step-by-Step Tutorial: Reusable Centralized Error System

Let us build a complete, reusable error-handling system in Node.js, Express.js, and Mongoose. All files below execute on the Node.js server.

Step 1: Create Custom Error Classes (src/utils/AppError.js)

Error.captureStackTrace keeps stack frames clean by excluding the constructor call itself.

Backend Source Code: src/utils/AppError.js

export class AppError extends Error {
  constructor(message, statusCode = 500, errorCode = 'INTERNAL_ERROR', details = null) {
    super(message);
    this.name = this.constructor.name;
    this.statusCode = statusCode;
    this.status = statusCode >= 400 && statusCode < 500 ? 'fail' : 'error';
    this.errorCode = errorCode;
    this.details = details;
    this.isOperational = true;
    Error.captureStackTrace(this, this.constructor);
  }
}

export class BadRequestError extends AppError {
  constructor(message = 'Bad request.', details = null) {
    super(message, 400, 'BAD_REQUEST', details);
  }
}

export class NotFoundError extends AppError {
  constructor(message = 'Requested resource was not found.') {
    super(message, 404, 'NOT_FOUND');
  }
}

export class ConflictError extends AppError {
  constructor(message = 'Resource conflict.') {
    super(message, 409, 'CONFLICT');
  }
}

export class ValidationAppError extends AppError {
  constructor(message = 'Validation failed.', details = []) {
    super(message, 422, 'VALIDATION_ERROR', details);
  }
}

Step 2: Create the 404 Not-Found Middleware (src/middleware/notFoundHandler.js)

Instead of responding directly inside a catch-all, forwarding a NotFoundError into next() ensures 404s use the exact same response format and logging pipeline as all other errors.

Backend Source Code: src/middleware/notFoundHandler.js

import { NotFoundError } from '../utils/AppError.js';

export const notFoundHandler = (req, res, next) => {
  next(new NotFoundError(`Route ${req.method} ${req.originalUrl} does not exist.`));
};

Step 3: Build Error Normalizers & Centralized Error Middleware (src/middleware/errorHandler.js)

Notice how raw Mongoose and JSON parser errors are converted into operational errors before deciding what to send in development versus production.

Backend Source Code: src/middleware/errorHandler.js

import { env } from '../config/env.js';
import {
  AppError,
  BadRequestError,
  ConflictError,
  ValidationAppError
} from '../utils/AppError.js';

const normalizeError = (err) => {
  if (err instanceof AppError) {
    return err;
  }

  if (err.type === 'entity.parse.failed' && err instanceof SyntaxError) {
    return new BadRequestError('Malformed JSON in request body.');
  }

  if (err.type === 'entity.too.large') {
    return new AppError('Request payload exceeds maximum allowed size.', 413, 'PAYLOAD_TOO_LARGE');
  }

  if (err.name === 'CastError') {
    return new BadRequestError(`Invalid format for field "${err.path}".`);
  }

  if (err.name === 'ValidationError' && err.errors) {
    const details = Object.values(err.errors).map((item) => ({
      field: item.path,
      message: item.message
    }));
    return new ValidationAppError('Input validation failed.', details);
  }

  if (err.code === 11000) {
    const duplicateFields = err.keyValue ? Object.keys(err.keyValue) : ['field'];
    return new ConflictError(`A record with that ${duplicateFields.join(', ')} already exists.`);
  }

  return err;
};

const logServerError = (err, req) => {
  const logEntry = {
    timestamp: new Date().toISOString(),
    requestId: req.requestId || 'unknown',
    method: req.method,
    path: req.originalUrl,
    statusCode: err.statusCode || 500,
    isOperational: Boolean(err.isOperational),
    message: err.message
  };

  if (!err.isOperational || logEntry.statusCode >= 500) {
    console.error('[SERVER ERROR]', JSON.stringify(logEntry));
    if (err.stack) {
      console.error(err.stack);
    }
  } else {
    console.warn('[OPERATIONAL ERROR]', JSON.stringify(logEntry));
  }
};

export const globalErrorHandler = (err, req, res, next) => {
  if (res.headersSent) {
    return next(err);
  }

  const normalized = normalizeError(err);
  const statusCode = normalized.statusCode || 500;
  const status = normalized.status || (statusCode < 500 ? 'fail' : 'error');

  logServerError(normalized, req);

  if (!env.isProduction) {
    return res.status(statusCode).json({
      status,
      errorCode: normalized.errorCode || 'INTERNAL_ERROR',
      message: normalized.message || 'Unexpected error.',
      details: normalized.details || undefined,
      requestId: req.requestId || null,
      stack: normalized.stack
    });
  }

  if (normalized.isOperational) {
    return res.status(statusCode).json({
      status,
      errorCode: normalized.errorCode || 'REQUEST_ERROR',
      message: normalized.message,
      details: normalized.details || undefined,
      requestId: req.requestId || null
    });
  }

  return res.status(500).json({
    status: 'error',
    errorCode: 'INTERNAL_SERVER_ERROR',
    message: 'Something went wrong on the server. Please try again later.',
    requestId: req.requestId || null
  });
};

Step 4: Use Custom Errors Inside Services & Controllers

Backend Source Code: src/services/memberService.js

import Member from '../models/Member.js';
import { ConflictError, NotFoundError } from '../utils/AppError.js';

export const registerMember = async ({ fullName, email }) => {
  const existing = await Member.findOne({ email: email.toLowerCase() });
  if (existing) {
    throw new ConflictError('That email address is already registered.');
  }

  return Member.create({ fullName, email });
};

export const getMemberById = async (memberId) => {
  const member = await Member.findById(memberId).select('-__v');
  if (!member) {
    throw new NotFoundError('Member account not found.');
  }
  return member;
};

Backend Source Code: src/controllers/memberController.js

import { asyncHandler } from '../utils/asyncHandler.js';
import { BadRequestError } from '../utils/AppError.js';
import * as memberService from '../services/memberService.js';

export const createMember = asyncHandler(async (req, res) => {
  const { fullName, email } = req.body;

  if (typeof fullName !== 'string' || fullName.trim().length < 2) {
    throw new BadRequestError('fullName must be at least 2 characters.');
  }

  if (typeof email !== 'string' || !email.includes('@')) {
    throw new BadRequestError('A valid email address is required.');
  }

  const created = await memberService.registerMember({
    fullName: fullName.trim(),
    email: email.trim().toLowerCase()
  });

  res.status(201).json({
    status: 'success',
    data: created
  });
});

export const getMember = asyncHandler(async (req, res) => {
  const member = await memberService.getMemberById(req.params.id);
  res.status(200).json({
    status: 'success',
    data: member
  });
});

Step 5: Register Global Handlers in app.js & Safety Nets in server.js

Backend Source Code: src/app.js

import express from 'express';
import memberRoutes from './routes/memberRoutes.js';
import { notFoundHandler } from './middleware/notFoundHandler.js';
import { globalErrorHandler } from './middleware/errorHandler.js';

const app = express();

app.disable('x-powered-by');
app.use(express.json({ limit: '10kb' }));

app.use('/api/v1/members', memberRoutes);

app.all('*', notFoundHandler);
app.use(globalErrorHandler);

export default app;

Backend Source Code: server.js (Process-level safety nets)

import { env } from './src/config/env.js';
import { connectDatabase, disconnectDatabase } from './src/config/database.js';
import app from './src/app.js';

process.on('uncaughtException', (err) => {
  console.error('[UNCAUGHT EXCEPTION] Shutting down immediately:', err.name, err.message);
  console.error(err.stack);
  process.exit(1);
});

let server;

const start = async () => {
  await connectDatabase();
  server = app.listen(env.port, () => {
    console.log(`Server running on port ${env.port} in ${env.nodeEnv} mode`);
  });
};

process.on('unhandledRejection', (reason) => {
  console.error('[UNHANDLED REJECTION] Initiating graceful shutdown:', reason);
  if (server) {
    server.close(async () => {
      await disconnectDatabase();
      process.exit(1);
    });
  } else {
    process.exit(1);
  }
});

start();

Real-World Use Cases

1. Frontend Error Handling & Localization

Returning a consistent errorCode (like COUPON_EXPIRED or VALIDATION_ERROR) lets browser and mobile frontends display friendly localized alerts instead of fragile string matching on English error messages.

2. Fast Incident Debugging with Request IDs

When a user reports an unexpected 500 error and shares the requestId from the UI, engineers can look up the exact server stack trace in seconds without ever exposing the stack trace to the user.

3. Clean Form Feedback with Field-Level Details

Normalizing Mongoose ValidationError objects into an array of { field, message } pairs allows client forms to highlight the exact invalid input box.

4. Zero-Crash Async Services

Combining asyncHandler, custom AppError subclasses, and centralized normalization eliminates duplicate try/catch boilerplate across dozens of controllers.

Common Mistakes, Security Notes, and Best Practices

Common Error-Handling Mistakes

  • Returning err.message blindly on 500 errors in production: Raw database or system errors like ECONNREFUSED 10.0.0.12:27017 reveal internal host IPs and infrastructure!
  • Returning 200 OK for errors: Always use proper 4xx or 5xx HTTP status codes so browser fetch() checks (response.ok) and monitoring alerts work properly.
  • Mounting error middleware above routes: Express only passes errors forward to middleware registered after the failing route. globalErrorHandler must sit last in app.js.
  • Swallowing errors inside empty catch (err) {} blocks: Silent catches hide real bugs and leave clients without feedback. Either handle meaningfully or pass to next(err).
  • Continuing to run after an uncaughtException: Once an uncaught synchronous exception hits the top of Node's event loop, process memory and connections may be in an inconsistent state—log and exit cleanly so a process manager restarts fresh.

Security & Best-Practice Notes

  • Never send stack traces in production: Gate stack strictly behind !env.isProduction.
  • Avoid generic leakage on auth errors: On login failures, return a neutral message such as "Invalid email or password" instead of revealing whether an email exists.
  • Check res.headersSent inside the global error handler: If an error occurs mid-stream after headers were already flushed, delegate to Express's built-in default handler via return next(err).
  • Sanitize logs: Ensure error loggers never dump raw req.body.password, cookies, or Authorization headers.

Short-Answer Questions

Think through each answer carefully before opening the explanation.

1. What is the key difference between an operational error and a programming error?

Operational errors are expected runtime problems (like invalid client input, missing documents, or duplicate database keys) that should produce informative 4xx client responses. Programming errors are unintended bugs in code (like TypeError) whose internal details must be logged privately and hidden behind a generic 500 message in production.

2. Why is a centralized error-handling middleware better than writing try/catch JSON responses in every controller?

Centralized error handling enforces one consistent JSON format, removes duplicated status/logging logic across controllers, ensures Mongoose/JSON parser errors are normalized uniformly, and guarantees production stack traces are never accidentally leaked.

3. How do synchronous thrown errors and rejected async promises differ in Express 4?

Synchronous errors thrown inside a route handler are caught automatically by Express and passed to error middleware. Rejected promises in async Express 4 handlers are not caught automatically unless wrapped with try/catch calling next(err) or an asyncHandler helper.

4. Why does including a requestId in both error logs and client JSON responses help support teams?

Clients only see a safe error message and the requestId, without sensitive stack traces. When they report an issue, engineers can search server logs by that exact requestId to inspect the full stack trace immediately.

5. Explain why Mongoose CastError and MongoDB code 11000 should be normalized in error middleware.

Without normalization, both look like unexpected 500 server errors and leak raw MongoDB details (like collection/index names). Normalizing them turns CastError into 400 Bad Request and 11000 into a clean 409 Conflict.
