Day 7: Rate Limiting

Without request throttling, a single automated script can hammer your login endpoint with 10,000 password guesses per minute, scrape your entire database, or exhaust your server's CPU and database connection pool. Rate limiting controls how many requests a client can make within a defined time window. Today you will learn how rate-limiting algorithms and headers work, how to configure IP-based and account-based limits safely in Express, how to protect sensitive endpoints, and what changes when scaling across multiple servers.

Learning Objectives

By the end of Day 7, you will be able to:

  • Explain what rate limiting is and why APIs rely on it for security, stability, and cost control.
  • Compare common window strategies (Fixed Window, Sliding Window, and Token Bucket) and their trade-offs.
  • Distinguish between IP-based rate limits and account/API-key-based rate limits.
  • Interpret standard rate-limit HTTP headers (RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset, Retry-After) and status code 429 Too Many Requests.
  • Configure global and route-specific rate limiters in Express using express-rate-limit.
  • Protect sensitive routes such as /login, /forgot-password, and contact forms without blocking legitimate users accidentally.
  • Explain why distributed deployments require shared stores like Redis rather than single-process memory.

Prerequisites

Before starting Day 7, make sure you understand:

  • Days 1, 2 & 6 Concepts: Express middleware ordering, app.set('trust proxy', 1), req.ip, and API security fundamentals.
  • HTTP Headers & Status Codes: Reading and writing custom headers and returning structured JSON error payloads.

Important Terminology and Definitions

Rate Limiting

A defensive middleware mechanism that restricts the maximum number of HTTP requests a client may perform during a specified time window.

Time Window

The measurement interval (for example, 15 minutes or 60 seconds) during which request counts are tracked before resetting or decaying.

429 Too Many Requests

The standard HTTP status code returned when a client exceeds its permitted request quota, typically paired with a Retry-After header.

Rate-Limit Key

The unique identifier used to bucket request counts—most commonly a client IP address (req.ip), an authenticated userId, or a combination of IP and email.

Fixed Window Counter

Tracks requests per discrete block of time (e.g., 12:00–12:15). Simple and memory-light, though bursts can briefly occur right across a window boundary.

Distributed Store (e.g., Redis)

An external shared fast in-memory store used when multiple Node.js instances run behind a load balancer so all instances share the same request counters.

Detailed Theory and Explanations

1. Why APIs Need Rate Limits

Rate limiting protects both security and infrastructure availability across four critical areas:

  • Brute-Force & Credential-Stuffing Prevention: Stops automated bots from trying thousands of passwords or 6-digit OTP verification codes on login and reset endpoints.
  • Resource & Database Protection: Prevents a buggy client loop or intentional flood from saturating CPU, memory, or MongoDB connections (application-layer Denial of Service).
  • Data Scraping Defense: Slows down bots attempting to download your entire product catalog or user directory.
  • Fair Usage & Cost Control: Protects paid downstream services—such as email providers, SMS gateways, or AI APIs—from runaway bills triggered by abusive traffic.

2. Requests per Time Window & Window Algorithms

Every rate limiter answers two questions: How many requests are allowed? (limit) and Over what duration? (windowMs). Common counting strategies include:

Algorithm How It Works Trade-Off
Fixed Window Resets a counter every N minutes (e.g., 100 requests per 15 minutes). Very fast and simple; slight edge-burst possible if 100 requests hit at 12:14:59 and 100 more at 12:15:01.
Sliding Window Tracks timestamps or weighted overlap across the rolling past N minutes. Smoother enforcement with no boundary spikes, at slightly higher memory/storage cost.
Token Bucket A bucket holds max tokens and refills steadily; each request consumes 1 token. Allows short legitimate bursts while enforcing a steady long-term average rate.

3. IP-Based vs. Account-Based Limits

IP-based limiting tracks requests by req.ip. It works on unauthenticated endpoints (like signup, login, or public search) because no user is logged in yet. However, remember two crucial caveats:

  • Reverse Proxies & trust proxy: In cloud hosting (Render, Railway, Nginx, Cloudflare), every request arrives at Node.js from the proxy's local IP unless app.set('trust proxy', 1) is set. Without trust proxy, all users appear to share the same proxy IP and one user's spam blocks everybody!
  • Shared NAT Networks: A university campus, corporate office, or mobile carrier often shares one public IP among hundreds of students or employees. Overly aggressive IP limits on general browsing routes can accidentally block innocent users sharing a network.

Account-based (or API-key-based) limiting runs after authentication middleware and keys counters by req.user.id (or ip + email on login). This prevents one user on shared office Wi-Fi from exhausting the quota of other coworkers, and stops an attacker from bypassing limits simply by switching VPN IPs while attacking a single victim's email account.

4. Rate-Limit Headers and Responses

Well-behaved APIs communicate quota status clearly in HTTP headers so legitimate frontend apps can back off gracefully:

  • RateLimit-Limit (draft-7/8 standard): Maximum requests permitted in the current window (e.g., 100).
  • RateLimit-Remaining: How many requests remain before throttling begins.
  • RateLimit-Reset: Seconds remaining until the window resets.
  • Retry-After: Sent on 429 Too Many Requests responses telling clients how many seconds to wait before retrying.

5. Applying Rate Limits to Selected Routes & Sensitive Endpoints

A single global limit is rarely ideal on its own. A normal browser user loading a dashboard might legitimately trigger 30 GET requests in a minute, whereas nobody legitimately submits 30 failed password attempts in a minute! Best practice uses tiered limiters:

  • General API Limiter: Moderate threshold across /api/v1 (for example, 100–200 requests per 15 minutes per IP).
  • Strict Auth / Sensitive Limiter: Tight threshold specifically on POST /api/v1/auth/login, POST /api/v1/auth/forgot-password, or POST /api/v1/contact (for example, 5–10 attempts per 15 minutes), optionally setting skipSuccessfulRequests: true on login so legitimate users who log in cleanly do not waste failure quota.

6. Distributed Deployment Considerations

By default, express-rate-limit stores counters inside your Node.js process RAM (MemoryStore). This works fine on a single server instance during development or small deployments. However, if you scale horizontally to 4 server containers behind a load balancer, each container has its own separate RAM—an attacker sending 20 requests could hit 5 requests per container without ever triggering a limit of 10!

In multi-instance production environments, configure a shared store such as Redis (for example, using rate-limit-redis) so all Node.js instances increment and read one central atomic counter.

7. Avoiding Accidental Denial of Service

Carelessly configured rate limits can lock out your own systems or real users. Avoid self-inflicted outages by:

  • Exempting health checks: Never apply strict rate limits to GET /api/v1/health; cloud load balancers ping health endpoints continuously and will restart your server if they receive 429!
  • Testing thresholds safely: Use realistic quotas and verify with controlled local requests rather than flooding live production services.
  • Using clean JSON 429 handlers: Return your standard API error structure so frontend clients handle throttling gracefully instead of crashing on plain-text error strings.

Step-by-Step Tutorial: Adding Tiered Rate Limiting to Express

Let us implement global and route-specific rate limiters using express-rate-limit inside a Node.js (server-side) Express API.

Step 1: Install express-rate-limit

Terminal Commands

npm install express-rate-limit

Configuration Template: .env.example

NODE_ENV=development
PORT=5000
RATE_LIMIT_WINDOW_MS=900000
RATE_LIMIT_MAX_GENERAL=100
RATE_LIMIT_MAX_AUTH=5

Step 2: Create Reusable Rate-Limiter Middleware (src/middleware/rateLimiters.js)

Notice how we use standardHeaders: 'draft-7', disable legacy headers, customize the JSON 429 response handler, and key the login limiter by both IP and normalized email so one shared office IP does not lock out other employees!

Backend Source Code: src/middleware/rateLimiters.js

import rateLimit from 'express-rate-limit';

const buildLimitHandler = (message) => {
  return (req, res, next, options) => {
    const retryAfterSeconds = Math.ceil(options.windowMs / 1000);
    res.setHeader('Retry-After', String(retryAfterSeconds));

    return res.status(options.statusCode).json({
      status: 'fail',
      errorCode: 'RATE_LIMIT_EXCEEDED',
      message,
      retryAfterSeconds
    });
  };
};

export const generalApiLimiter = rateLimit({
  windowMs: Number(process.env.RATE_LIMIT_WINDOW_MS) || 15 * 60 * 1000,
  limit: Number(process.env.RATE_LIMIT_MAX_GENERAL) || 100,
  standardHeaders: 'draft-7',
  legacyHeaders: false,
  skip: (req) => req.path === '/health',
  handler: buildLimitHandler('Too many requests from this IP. Please slow down and try again later.')
});

export const authAttemptLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: Number(process.env.RATE_LIMIT_MAX_AUTH) || 5,
  standardHeaders: 'draft-7',
  legacyHeaders: false,
  skipSuccessfulRequests: true,
  keyGenerator: (req) => {
    const email = typeof req.body?.email === 'string' ? req.body.email.trim().toLowerCase() : 'anonymous';
    return `${req.ip}:${email}`;
  },
  handler: buildLimitHandler('Too many failed authentication attempts. Please wait 15 minutes before retrying.')
});

export const accountActionLimiter = rateLimit({
  windowMs: 60 * 60 * 1000,
  limit: 20,
  standardHeaders: 'draft-7',
  legacyHeaders: false,
  keyGenerator: (req) => {
    return req.user?.id ? `user:${req.user.id}` : req.ip;
  },
  handler: buildLimitHandler('Hourly action limit reached for this account.')
});

Step 3: Mount Health Checks, Global Limiter, and Route-Specific Limiters

Mount app.set('trust proxy', 1) before rate limiters so req.ip resolves accurately behind proxies, and attach authAttemptLimiter specifically to sensitive routes.

Backend Source Code: src/routes/authRoutes.js

import express from 'express';
import { authAttemptLimiter } from '../middleware/rateLimiters.js';

const router = express.Router();

router.post('/login', authAttemptLimiter, (req, res) => {
  const { email, password } = req.body;

  if (email === 'demo@example.com' && password === 'SamplePass123!') {
    return res.status(200).json({
      status: 'success',
      message: 'Login successful.'
    });
  }

  return res.status(401).json({
    status: 'fail',
    message: 'Invalid email or password.'
  });
});

router.post('/forgot-password', authAttemptLimiter, (req, res) => {
  return res.status(200).json({
    status: 'success',
    message: 'If that account exists, a reset link has been queued.'
  });
});

export default router;

Backend Source Code: src/app.js

import express from 'express';
import helmet from 'helmet';
import { generalApiLimiter, accountActionLimiter } from './middleware/rateLimiters.js';
import authRoutes from './routes/authRoutes.js';

const app = express();

app.disable('x-powered-by');
app.set('trust proxy', 1);

app.use(helmet());
app.use(express.json({ limit: '10kb' }));

app.get('/api/v1/health', (req, res) => {
  res.status(200).json({ status: 'ok' });
});

app.use('/api/v1', generalApiLimiter);
app.use('/api/v1/auth', authRoutes);

app.post('/api/v1/reports/export', (req, res, next) => {
  req.user = { id: 'usr_demo_01' };
  next();
}, accountActionLimiter, (req, res) => {
  res.status(200).json({ status: 'success', message: 'Report export started.' });
});

export default app;

Step 4: Safely Test Normal vs. Excessive Requests Locally

Never run aggressive loops against third-party websites. Test safely against your own local http://localhost:5000 server using curl.

Terminal Test Commands (Bash loop sending 6 consecutive failed logins locally)

for i in {1..6}; do
  echo "Attempt $i:"
  curl -i -s -X POST http://localhost:5000/api/v1/auth/login \
    -H "Content-Type: application/json" \
    -d '{"email":"demo@example.com","password":"wrong"}' | grep -E "HTTP/|ratelimit|retry-after|\{"
done

Step 5: Notes on Distributed Production Store (Redis)

When scaling to multiple Node.js instances behind a load balancer, swap the default in-memory store for a shared Redis store (rate-limit-redis + redis) passed via the store option inside rateLimit({ store: new RedisStore(...), ... }).

Real-World Use Cases

1. Login & 2FA OTP Protection

A 6-digit OTP has only 1,000,000 combinations. Tight rate limiting (e.g., 5 attempts per 15 minutes) stops bots from brute-forcing verification codes within seconds.

2. Preventing Email/SMS Abuse

Without strict limits on /forgot-password or /contact, an attacker can trigger thousands of outbound emails or SMS messages, costing real money and ruining domain sender reputation.

3. Tiered SaaS API Quotas

Public developer APIs use account/API-key-based limiters to grant free-tier users 60 requests/minute and paid-tier users 1,000 requests/minute.

4. Heavy Compute Endpoint Shielding

Endpoints that generate PDFs, export large CSVs, or run complex search aggregations receive lower per-user rate limits so one user cannot degrade performance for everyone else.

Common Mistakes, Security Notes, and Best Practices

Common Rate-Limiting Mistakes

  • Forgetting app.set('trust proxy', 1) in cloud hosting: Without it, Express sees the load balancer's IP for every single visitor, causing one user to trigger 429 for the entire website!
  • Rate limiting health-check endpoints: Blocking /health causes container orchestrators to mark healthy servers as dead and restart them repeatedly.
  • Using one ultra-tight limit globally: Setting 5 requests/minute on all routes breaks normal page loads that fetch user profiles, notifications, and settings in parallel.
  • Trusting client-supplied spoofing headers: Never manually trust arbitrary req.headers['x-forwarded-for'] strings without configuring Express trust proxy properly—attackers can fake custom headers to bypass IP limits!

Security & Best-Practice Notes

  • Run rate limiting BEFORE expensive work: Mount rate limiters above database queries and bcrypt.compare() so blocked bots do not consume CPU or DB connections.
  • Combine ip + email on login limiters: Protects shared NAT networks while still stopping distributed password guessing against a single user account.
  • Use skipSuccessfulRequests: true thoughtfully: Helpful on login endpoints so normal users logging in multiple times a day are not penalized while failed guesses still hit the cap.
  • Remember distributed state: Use a shared store like Redis whenever running clustered Node processes or multiple replicas.

Hands-On Exercises

  1. Inspect Rate-Limit Headers: Make 3 consecutive GET requests to an endpoint protected by generalApiLimiter with curl -i and observe how RateLimit-Remaining decrements on each call.
  2. Health Check Exemption Test: Set a temporary low limit of 3 requests on generalApiLimiter, call GET /api/v1/health 5 times, and verify it always returns 200 OK due to the skip rule.
  3. Account-Based vs. IP-Based Simulation: Test accountActionLimiter by sending requests with two different simulated user IDs from the same localhost IP and verify each user gets an independent quota.
  4. Verify skipSuccessfulRequests: Send 5 successful logins to /api/v1/auth/login and verify none trigger 429, then send 5 failed logins and verify the 6th fails with 429 Too Many Requests.

Short-Answer Questions

Think through each answer carefully before expanding the explanation.

1. What problem does rate limiting solve on password-reset and contact-form endpoints?

It prevents bots from triggering thousands of automated emails or SMS messages, protecting your server against spam abuse, wasted third-party API costs, and email sender reputation damage.

2. Compare IP-based rate limiting and account-based rate limiting.

IP-based rate limiting identifies clients by network IP address and works before authentication (such as on signup/login), though users behind shared NAT Wi-Fi share an IP. Account-based limiting identifies authenticated users via req.user.id or API key, giving each user a fair, independent quota.

3. What is the boundary burst trade-off of a Fixed Window counter?

If a fixed window allows 100 requests per minute, a client could send 100 requests at 12:00:59 and another 100 requests at 12:01:01—creating 200 requests in two seconds across the reset boundary. Sliding window and token bucket algorithms smooth out this spike.

4. Why is trust proxy essential before deploying an Express rate limiter to production?

Behind a cloud load balancer or reverse proxy, Express sees the proxy's internal IP in req.ip unless trust proxy is configured. Without it, all internet users share one counter and quickly block one another.

5. Explain why distributed Node.js deployments require Redis (or another shared store) for rate limiting.

Each Node.js container or cluster worker has isolated RAM. A shared Redis store ensures every server instance reads and increments the same central counter atomically so limits remain accurate regardless of which server handles each request.

Day 7 Revision Summary

  • Rate limiting caps requests per time window to defend against brute-force attacks, scraping, DoS, and runaway costs.
  • Always set app.set('trust proxy', 1) behind reverse proxies so req.ip reflects the real client.
  • Apply tiered limiters: moderate global limits across /api, strict limits on sensitive routes (/login, /forgot-password, /contact), and exemptions for /health probes.
  • Return HTTP 429 Too Many Requests with RateLimit-* and Retry-After headers in a consistent JSON format.
  • Use a shared store like Redis when running multiple Node.js instances in production.
