Day 8: CORS (Cross-Origin Resource Sharing)

Almost every backend developer eventually hits this famous red error in the browser console: "Access to fetch at 'http://localhost:5000/api/v1/projects' from origin 'http://localhost:5500' has been blocked by CORS policy." Many developers blindly paste app.use(cors()) without understanding what is happening or why that shortcut can create serious security risks when cookies or private APIs are involved. Today you will learn the Same-Origin Policy, how CORS preflight OPTIONS requests work, how to configure trusted origin allow-lists safely across development and production, and why CORS is never a substitute for authentication.

Learning Objectives

By the end of Day 8, you will be able to:

  • Define an origin and explain the browser's Same-Origin Policy (SOP).
  • Explain what CORS is, why web browsers enforce it, and why non-browser tools like curl or Postman do not.
  • Distinguish between simple requests and preflighted requests (using HTTP OPTIONS).
  • Configure allowed origins, HTTP methods, request headers, and credentials cleanly in Express using cors.
  • Understand why Access-Control-Allow-Origin: * is incompatible with credentials: true (cookies/auth headers).
  • Separate development origin lists from strict production origin allow-lists using environment variables.
  • Debug common CORS errors accurately and explain why CORS is not API authentication or security replacement.

Prerequisites

Before starting Day 8, make sure you understand:

  • Browser vs. Server Execution: Browser-side JavaScript runs inside Chrome/Firefox/Safari on a frontend origin (such as http://localhost:5500 or https://myapp.netlify.app) and calls fetch() to communicate with your Express server on a backend origin (such as http://localhost:5000 or https://api.myapp.com).
  • Days 1, 2 & 6 Concepts: Express middleware ordering, HTTP headers, and API security fundamentals.

Important Terminology and Definitions

Origin

The exact combination of protocol (scheme) + hostname (domain) + port. For example, http://localhost:5500 and http://localhost:5000 are two different origins because their ports differ.

Same-Origin Policy (SOP)

A fundamental browser security rule that prevents JavaScript on one website from freely reading responses from another origin unless the target server explicitly grants permission.

CORS

Cross-Origin Resource Sharing—an HTTP header protocol that lets a backend server tell the browser which external origins, methods, and headers are permitted to read its responses.

Preflight Request (OPTIONS)

An automatic check request sent by the browser before the real request whenever a cross-origin call uses non-simple methods (like PUT/DELETE), JSON Content-Type, or custom headers like Authorization.

Credentials Mode

Sending cookies, TLS client certificates, or HTTP auth across origins (credentials: 'include' in browser fetch, paired with Access-Control-Allow-Credentials: true on the server).

Vary: Origin

A response header telling caches/CDNs that the Access-Control-Allow-Origin value depends on the incoming Origin request header so cached responses are not served to the wrong domain.

Detailed Theory and Explanations

1. What an Origin Is & What the Same-Origin Policy Protects

Two URLs share the same origin only if all three components match identically:

Frontend URL Backend API URL Same Origin? Reason
https://app.example.com/home https://app.example.com/api/v1/users Yes Same scheme (https), host (app.example.com), and port (443)
http://localhost:5500 http://localhost:5000 No (Cross-Origin) Different ports (5500 vs 5000)
http://example.com https://example.com No (Cross-Origin) Different schemes (http vs https)
https://example.com https://api.example.com No (Cross-Origin) Different hostnames (subdomain counts as a separate origin)

Why does the browser enforce the Same-Origin Policy? Suppose you are logged into your bank at https://bank.example (so your browser holds a session cookie). Then you visit an untrusted blog at https://evil-blog.example. Without SOP, JavaScript on that malicious page could silently run fetch('https://bank.example/api/balance', { credentials: 'include' }) and read your private bank account balance! SOP blocks the malicious page from reading that cross-origin response unless bank.example explicitly allows it via CORS headers.

2. How CORS Works & Key HTTP Headers

When a browser makes a cross-origin request, it automatically attaches an Origin: https://frontend.example header. Your Express server inspects that Origin and responds with CORS headers:

  • Access-Control-Allow-Origin: Specifies the single permitted origin (e.g., https://frontend.example) or * for public unauthenticated APIs.
  • Access-Control-Allow-Methods: Lists allowed HTTP methods during preflight (e.g., GET,POST,PATCH,DELETE).
  • Access-Control-Allow-Headers: Lists permitted custom request headers (e.g., Content-Type,Authorization).
  • Access-Control-Allow-Credentials: Set to true when cookies or auth credentials are allowed cross-origin.
  • Access-Control-Max-Age: Caches preflight OPTIONS results in the browser (in seconds, e.g., 600) so the browser does not send an OPTIONS call before every single API request.

3. Simple Requests vs. Preflight (OPTIONS) Requests

Browsers divide cross-origin requests into two categories:

  • Simple Requests: Only GET, HEAD, or POST, using only safe headers and Content-Type equal to application/x-www-form-urlencoded, multipart/form-data, or text/plain. The browser sends the request directly and checks the response's Access-Control-Allow-Origin header before letting JavaScript read the body.
  • Preflighted Requests: Any request using PUT, PATCH, DELETE, Content-Type: application/json, or custom headers like Authorization: Bearer .... Before sending the actual request, the browser first sends an automatic OPTIONS preflight request asking the server: "Is origin X allowed to send a PATCH request with Authorization and Content-Type: application/json?" Only if the server replies 204/200 with matching Access-Control-Allow-* headers does the browser send the real request!

4. Credentials, Cookies, and Why * Fails with Credentials

If your frontend sends cookies or credentials using fetch(url, { credentials: 'include' }), the browser enforces a strict rule: the server cannot respond with Access-Control-Allow-Origin: *. Allowing every website on the internet to read credentialed responses would defeat the Same-Origin Policy!

Instead, when credentials: true is enabled in Express, your CORS middleware must echo back the exact validated origin (for example, Access-Control-Allow-Origin: https://app.example.com) plus Access-Control-Allow-Credentials: true and Vary: Origin.

5. Development vs. Production Configuration & Trusted Origins

During local development, your frontend might run on http://localhost:5500 or http://localhost:5173 while your API runs on http://localhost:5000. In production, you must restrict origins strictly to your deployed frontend domain(s) (for example, https://arslan-weblab.netlify.app) loaded from an environment variable like CORS_ORIGINS. Never leave localhost origins enabled in production, and never dynamically reflect every incoming req.headers.origin blindly without checking an allow-list!

6. Why CORS Is NOT Authentication or API Security

This is one of the most critical misconceptions in backend development: CORS is enforced exclusively by web browsers to protect browser users. Non-browser HTTP clients—such as curl, Postman, Python scripts, or another Node.js server—completely ignore CORS headers and can send requests without an Origin header or fake any Origin header they want!

Therefore, CORS never secures private API endpoints by itself. Every protected endpoint must still enforce server-side authentication, authorization, input validation, and rate limiting.

Diagram: CORS Preflight (OPTIONS) & Actual Request Flow

Follow the two-step exchange between a browser running on http://localhost:5500 and your Express API on http://localhost:5000:

Step 1 • Browser Preflight Check Browser (http://localhost:5500) → OPTIONS /api/v1/notes/1 Headers: Origin: http://localhost:5500, Access-Control-Request-Method: PATCH, Access-Control-Request-Headers: content-type,authorization
↓
Origin Allowed Express cors → 204 No Content Returns matching Access-Control-Allow-Origin, Allow-Methods, Allow-Headers, Vary: Origin
Origin Not in Allow-List Rejected (No Allow-Origin Header) Browser blocks JavaScript from making/reading the request and logs a CORS error
↓
Step 2 • Actual API Request Browser → PATCH /api/v1/notes/1 → Express Controller → 200 OK Browser verifies response headers and delivers JSON safely to frontend fetch()

Step-by-Step Tutorial: Connecting a Different-Origin Frontend to Express

In this tutorial, you will run a Node.js/Express backend on http://localhost:5000 and a separate browser-side HTML/JS frontend on http://localhost:5500, connected via a strict, environment-driven CORS policy.

Step 1: Install cors in Your Backend Project

Terminal Commands (Inside Backend Folder)

npm install cors

Configuration Template: .env.example

NODE_ENV=development
PORT=5000
CORS_ORIGINS=http://localhost:5500,http://127.0.0.1:5500

Step 2: Build a Trusted-Origin CORS Configuration Module (src/config/corsOptions.js)

Notice how we parse comma-separated origins from CORS_ORIGINS, allow requests without an Origin header (such as curl, Postman, or server health probes) only when appropriate, and reject untrusted browser origins cleanly.

Backend Source Code: src/config/corsOptions.js (Runs on Node.js)

const parseAllowedOrigins = () => {
  const raw = process.env.CORS_ORIGINS || '';
  return raw
    .split(',')
    .map((origin) => origin.trim())
    .filter(Boolean);
};

export const buildCorsOptions = () => {
  const allowedOrigins = new Set(parseAllowedOrigins());

  return {
    origin: (requestOrigin, callback) => {
      if (!requestOrigin) {
        return callback(null, true);
      }

      if (allowedOrigins.has(requestOrigin)) {
        return callback(null, true);
      }

      const corsError = new Error(`Origin ${requestOrigin} is not allowed by CORS policy.`);
      corsError.statusCode = 403;
      return callback(corsError);
    },
    methods: ['GET', 'POST', 'PATCH', 'PUT', 'DELETE', 'OPTIONS'],
    allowedHeaders: ['Content-Type', 'Authorization', 'X-Request-Id'],
    exposedHeaders: ['X-Request-Id', 'RateLimit-Limit', 'RateLimit-Remaining', 'RateLimit-Reset'],
    credentials: true,
    maxAge: 600,
    optionsSuccessStatus: 204
  };
};

Step 3: Mount cors Correctly in src/app.js

Register cors before your routes and rate limiters (or right after security headers) so preflight OPTIONS requests succeed immediately! Also note: if you use helmet() and serve images/assets cross-origin, configure crossOriginResourcePolicy: { policy: 'cross-origin' } only where needed.

Backend Source Code: src/app.js (Runs on Node.js)

import 'dotenv/config';
import express from 'express';
import helmet from 'helmet';
import cors from 'cors';
import { buildCorsOptions } from './config/corsOptions.js';

const app = express();
const corsMiddleware = cors(buildCorsOptions());

app.disable('x-powered-by');
app.use(helmet());
app.use(corsMiddleware);
app.options('*', corsMiddleware);
app.use(express.json({ limit: '10kb' }));

const items = [
  { id: 1, title: 'Configure Trusted Origins', status: 'done' },
  { id: 2, title: 'Test Preflight OPTIONS Request', status: 'in-progress' }
];

app.get('/api/v1/items', (req, res) => {
  res.status(200).json({
    status: 'success',
    originSeenByServer: req.get('origin') || 'none',
    data: items
  });
});

app.patch('/api/v1/items/:id', (req, res) => {
  const id = Number(req.params.id);
  const item = items.find((entry) => entry.id === id);

  if (!item) {
    return res.status(404).json({ status: 'fail', message: 'Item not found.' });
  }

  if (typeof req.body?.status === 'string') {
    item.status = req.body.status;
  }

  return res.status(200).json({ status: 'success', data: item });
});

app.use((err, req, res, next) => {
  const statusCode = err.statusCode || 500;
  res.status(statusCode).json({
    status: statusCode < 500 ? 'fail' : 'error',
    message: err.message
  });
});

const PORT = Number(process.env.PORT) || 5000;
app.listen(PORT, () => {
  console.log(`CORS-enabled API listening on http://localhost:${PORT}`);
});

Step 4: Create a Separate Browser-Side Frontend on Origin http://localhost:5500

Remember the core rule: this HTML/JS file runs inside a web browser on port 5500, and sends cross-origin fetch() calls to your Express backend on port 5000.

Browser-Side Frontend Code: frontend-demo/index.html (Serve on port 5500, e.g., VS Code Live Server or npx serve -l 5500)

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>CORS Frontend Client Demo</title>
</head>
<body>
  <h1>Cross-Origin Client (Port 5500)</h1>
  <button id="loadBtn" type="button">Load Items (GET)</button>
  <button id="updateBtn" type="button">Update Item 2 (PATCH Preflight)</button>
  <pre id="output"></pre>

  <script>
    const API_BASE = 'http://localhost:5000/api/v1';
    const output = document.getElementById('output');

    document.getElementById('loadBtn').addEventListener('click', async () => {
      const response = await fetch(`${API_BASE}/items`, {
        method: 'GET',
        credentials: 'include'
      });
      const json = await response.json();
      output.textContent = JSON.stringify(json, null, 2);
    });

    document.getElementById('updateBtn').addEventListener('click', async () => {
      const response = await fetch(`${API_BASE}/items/2`, {
        method: 'PATCH',
        credentials: 'include',
        headers: {
          'Content-Type': 'application/json',
          'Authorization': 'Bearer sample-demo-token'
        },
        body: JSON.stringify({ status: 'done' })
      });
      const json = await response.json();
      output.textContent = JSON.stringify(json, null, 2);
    });
  </script>
</body>
</html>

Real-World Use Cases

1. Separate Frontend Hosting + Backend API Hosting

Deploying a static frontend on Netlify/Vercel (https://myapp.netlify.app) and an Express API on Render/Railway (https://api.myapp.com) puts them on different origins, requiring a trusted CORS configuration.

2. Cookie-Based Authentication Across Subdomains

When https://app.company.com authenticates against https://api.company.com using HttpOnly cookies, CORS must explicitly allow that exact origin with credentials: true (never wildcard *).

3. Public Read-Only Open Data APIs

A public weather or currency API that requires no cookies or user sessions can intentionally set origin: '*' and methods: ['GET'] so any website worldwide can read public data.

4. Exposing Custom Pagination or Rate-Limit Headers

Without listing custom headers in exposedHeaders, browser JavaScript running response.headers.get('X-Request-Id') will receive null even though the header appears in DevTools Network tab!

Common Mistakes, Security Notes, and Best Practices

Common CORS Errors & Mistakes

  • Using origin: '*' together with credentials: true: Browsers reject this combination immediately! Always specify explicit allowed origins when sending cookies or credentials.
  • Trailing slashes in CORS_ORIGINS: Browsers send Origin: https://myapp.com without a trailing slash. Putting https://myapp.com/ in your allow-list causes mismatches!
  • Forgetting allowedHeaders for custom headers: If your frontend sends X-Client-Version or Authorization and your CORS config omits it from allowedHeaders, preflight fails.
  • Mounting auth or rate-limiters blindly before OPTIONS handling: If an auth middleware rejects unauthenticated OPTIONS preflights with 401, browsers block the real request! Always mount cors before route auth guards.
  • Blindly reflecting origin: true in production: Passing origin: true tells the cors package to mirror any attacker's Origin back with Allow-Credentials: true—a major security flaw!

Security & Best-Practice Notes

  • CORS is NOT API authentication: Never rely on CORS to protect private endpoints—curl and scripts bypass CORS completely. Always verify tokens/permissions on the server.
  • Maintain strict production allow-lists: Load exact production origins from CORS_ORIGINS and remove localhost origins in production.
  • Understand Vary: Origin: The cors library automatically sets Vary: Origin when dynamic origins are used so CDNs do not cache one origin's header for another.
  • Set maxAge wisely: Caching preflights for 600 seconds avoids doubling network round-trips on active single-page apps.

Hands-On Exercises

  1. Reproduce & Fix a Missing-Origin Error: Run the frontend HTML demo on port 5500 with CORS_ORIGINS set only to http://localhost:3000. Inspect the exact error in browser DevTools Console and Network tab, then add http://localhost:5500 and re-test.
  2. Test Wildcard + Credentials Rejection: Temporarily configure origin: '*' with credentials: true in a local test script and send a fetch(..., { credentials: 'include' }) call to observe the browser's exact rejection rule.
  3. Preflight Header Experiment: Add a custom header X-App-Client: web to a browser fetch() call while omitting it from allowedHeaders. Watch the OPTIONS request fail, then add X-App-Client to allowedHeaders to fix it.
  4. Expose Custom Response Headers: Read response.headers.get('X-Request-Id') in browser JS before and after adding 'X-Request-Id' to exposedHeaders.

Short-Answer Questions

Think through each answer carefully before opening the explanation.

1. Define what constitutes an "origin" and give an example of two URLs with different origins on localhost.

An origin is the exact combination of scheme (protocol), host, and port. On localhost, http://localhost:5500 and http://localhost:5000 have different origins because their port numbers differ.

2. Explain why browsers send an OPTIONS preflight request before a cross-origin PATCH request with Authorization.

PATCH and custom headers like Authorization are non-simple requests. The browser sends an automatic OPTIONS preflight first to ask the server whether the frontend origin, method, and headers are allowed before sending the actual mutation request.

3. Why can you not combine Access-Control-Allow-Origin: * with credentials: true?

If wildcard * worked with credentials, any malicious website could instruct a victim's browser to send credentialed requests with cookies and read private responses. Browsers require an explicit single matching origin when credentials are enabled.

4. Why does an API that works cleanly in Postman or curl sometimes fail with a CORS error in a browser?

Postman and curl are non-browser clients and do not enforce the browser's Same-Origin Policy or send/validate CORS headers. Browsers enforce CORS strictly when frontend JavaScript calls a different origin.

5. Explain why CORS does not protect a backend endpoint against unauthorized access from scripts.

CORS is only a browser security policy. Attackers using Python, Node.js, or curl can hit your API directly without obeying CORS headers—meaning real server-side authentication and authorization are always required.

Day 8 Revision Summary

  • An origin is scheme + host + port; the browser's Same-Origin Policy blocks cross-origin response reading by default.
  • CORS uses HTTP headers (Access-Control-Allow-Origin, Allow-Methods, Allow-Headers, Allow-Credentials) to grant controlled cross-origin access.
  • Non-simple requests trigger an automatic OPTIONS preflight request—mount cors before auth middleware so preflights are not blocked.
  • Never combine origin: '*' or blind origin: true with credentials: true; use an explicit environment-driven allow-list.
  • CORS protects browser users only and never replaces server-side authentication, authorization, or rate limiting.
