Day 6: API Security

A functional API that lacks security is an open invitation for data breaches, account takeovers, and service outages. Because backend APIs are directly exposed to the internet, attackers can bypass your browser UI completely and send crafted HTTP requests directly to your endpoints using scripts or curl. Today you will learn the core threats facing Node.js, Express, and MongoDB APIs—and how to build defense-in-depth protections through validation, sanitization, credential hashing, secure headers, least privilege, and dependency hygiene.

Learning Objectives

By the end of Day 6, you will be able to:

  • Identify common backend API risks including NoSQL injection, Broken Object Level Authorization (BOLA), mass assignment, and sensitive data exposure.
  • Implement strict input validation and sanitize payloads against MongoDB operator injection ($ and . keys).
  • Protect environment variables and credentials from leaking into Git history, logs, or API responses.
  • Hash passwords safely using slow salted algorithms (bcryptjs / scrypt) and prevent user-enumeration via safe error messages.
  • Harden HTTP response headers using helmet and payload limits.
  • Distinguish Authentication from Authorization and enforce the Principle of Least Privilege, including resource ownership checks.
  • Maintain dependency and configuration hygiene using npm audit and lockfiles.

Prerequisites

Before starting Day 6, make sure you are comfortable with:

  • Days 1–5 Concepts: Express middleware pipelines, layered services/controllers, and centralized AppError handling.
  • HTTP Headers & Status Codes: Understanding 400, 401, 403, and standard headers like Authorization and Content-Type.
  • Client vs. Server Trust Boundary: Understanding that browser-side HTML/JS validation only helps UX; attackers can bypass browsers and send raw HTTP requests straight to Node.js, so all security enforcement must happen on the server.

Important Terminology and Definitions

Defense in Depth

A security strategy that layers multiple independent safeguards—headers, payload limits, validation, authentication, authorization, and database protections—so one failure does not compromise the system.

NoSQL Injection

An attack where malicious JSON objects containing MongoDB operators (such as { "$ne": null } or { "$gt": "" }) are injected into queries to bypass authentication or dump records.

BOLA (Broken Object Level Authorization)

A critical vulnerability where an authenticated user accesses or modifies another user's record simply by changing an :id parameter in the URL because the server never checked ownership.

Principle of Least Privilege

Giving every user, API token, and database account only the minimum permissions and fields required to perform its intended job—nothing more.

Salted Password Hashing

Transforming a plaintext password with a unique random salt through a deliberately slow one-way algorithm (like bcrypt or argon2) so stored hashes cannot be reversed or cracked quickly.

Account Enumeration

An information leak where login or password-reset errors reveal whether an email exists (e.g., "Email not found" vs. "Wrong password"), letting attackers build a list of registered users.

Detailed Theory and Explanations

1. Common API Security Risks

Risk How It Happens Defense
NoSQL Operator Injection Passing { email: req.body.email } directly to User.findOne() when req.body.email is { "$gt": "" }. Validate strict string types (typeof email === 'string') and strip keys starting with $ or containing ..
BOLA / Missing Ownership Check Checking requireAuth on GET /invoices/:id, but failing to verify invoice.ownerId === req.user.id. Query with both ID and owner (_id + ownerId) or verify ownership before returning/mutating data.
Mass Assignment Passing entire req.body into User.create(req.body) so a user supplies "role": "admin". Allow-list only permitted fields explicitly before calling Mongoose.
Sensitive Data Exposure Returning full Mongoose documents containing passwordHash, tokens, or internal flags. Set select: false on sensitive schema fields and use explicit DTO formatters.
Credential & Secret Leaks Hardcoding DB URIs or JWT secrets in source code or committing .env to Git. Store secrets in environment variables, ignore .env in .gitignore, and validate at startup.

2. Input Validation & Sanitization

Validation checks that incoming data matches the exact shape, type, and constraints expected (for example, email must be a string matching email format and under 120 characters). Sanitization cleans or neutralizes dangerous characters or structures before your app stores or queries them.

In MongoDB/Express APIs, JSON bodies allow nested objects! If an endpoint expects a string username and an attacker sends { "username": { "$ne": "" } }, Mongoose queries can behave unexpectedly unless you both validate primitive types and strip dangerous MongoDB operator keys (keys beginning with $ or containing .).

3. Secure Handling of Environment Variables

  • Never put passwords, API keys, JWT secrets, or database connection strings inside JavaScript files.
  • Add .env to .gitignore before your very first commit. If a secret is ever committed—even once—assume it is compromised and rotate it immediately.
  • Use separate credentials for development, staging, and production environments.
  • On the database side, create a dedicated MongoDB user scoped only to your application's database with read/write rights rather than using a cluster-wide root admin account.

4. Password and Credential Safety

Never store plaintext passwords and never use fast general-purpose hashes like SHA-256 or MD5 for passwords—modern GPUs can guess billions of SHA-256 hashes per second. Always use an adaptive, salted, slow password-hashing function such as bcrypt (cost factor 10–12), Argon2id, or Node's built-in crypto.scrypt.

Furthermore, mark passwordHash with select: false in your Mongoose schema so normal User.find() queries never fetch password hashes accidentally, and compare hashes with constant-time functions (bcrypt.compare or crypto.timingSafeEqual) to avoid timing side-channel leaks.

5. Secure HTTP Headers with helmet

Every HTTP response includes metadata headers that instruct browsers how to handle your responses safely. By default, Express sends X-Powered-By: Express and omits protective headers. Installing and mounting helmet() sets crucial security headers automatically:

  • X-Content-Type-Options: nosniff: Prevents browsers from MIME-sniffing files into executable scripts.
  • X-Frame-Options: SAMEORIGIN / frame-ancestors: Protects against clickjacking attacks.
  • Strict-Transport-Security (HSTS): Instructs browsers to connect exclusively over HTTPS.
  • Content-Security-Policy (CSP): Restricts where scripts, styles, and frames can load from.
  • Removes X-Powered-By to reduce framework fingerprinting.

6. Authentication, Authorization & Least Privilege

Authentication answers "Who are you?" (returning 401 Unauthorized if missing/invalid). Authorization answers "Are you allowed to touch this specific resource or action?" (returning 403 Forbidden if denied).

Applying the Principle of Least Privilege means:

  • New user registrations always default to the lowest role ('member'), ignoring any role property sent in req.body.
  • Users can only view, edit, or delete records where record.ownerId matches req.user.id (unless an explicit admin role is verified).
  • Responses project only the fields needed by that endpoint instead of dumping entire database objects.

7. Safe Error Messages & Dependency Hygiene

Safe error messages help real users without educating attackers. On login endpoints, always return the exact same neutral message—such as "Invalid email or password."—whether the email was not found or the password did not match. Never return database table names, index errors, or stack traces in production.

Finally, keep your dependencies clean: commit package-lock.json so builds use verified package versions, run npm audit regularly to spot known CVEs, remove unused packages, and avoid unmaintained third-party libraries.

Diagram: Defense-in-Depth API Security Layers

Security works best in concentric layers—if a request fails any gate, it is stopped safely before reaching your database:

Layer 1 • Perimeter & Headers helmet() + Payload Limits + HTTPS Sets protective HTTP headers, hides X-Powered-By, caps JSON body to 10kb
↓
Layer 2 • Sanitization & Validation Strip $ / . Keys + Explicit Schema Allow-Listing Blocks NoSQL operator injection and mass assignment before logic runs
↓
Layer 3 • Identity & Least Privilege Authentication (401) → Role + Ownership Check (403) Verifies identity and confirms user owns the target record (prevents BOLA)
↓
Layer 4 • Data & Output Safety Salted Password Hashing + Field Projection + Safe Errors Hides passwordHash/__v, returns clean DTOs, suppresses stack traces in production

Step-by-Step Tutorial: Hardening an Express & MongoDB API

Before: Vulnerable Patterns to Spot

Look at how many security holes exist in just 12 lines of careless code:

Insecure Anti-Pattern (Do NOT use in production)

app.use(express.json());

app.post('/api/register', async (req, res) => {
  const user = await User.create(req.body);
  res.json(user);
});

app.post('/api/login', async (req, res) => {
  const user = await User.findOne({ email: req.body.email });
  if (!user) return res.status(404).json({ message: 'No user with that email' });
  if (user.password !== req.body.password) return res.status(401).json({ message: 'Wrong password' });
  res.json({ user });
});

Problems here: no payload size cap, no helmet headers, mass assignment on User.create(req.body), plaintext passwords, NoSQL injection risk if req.body.email is an object, account enumeration on login messages, and leaking the entire user document including password!

Step 2: Build Recursive NoSQL Operator Sanitization Middleware

This middleware removes any key starting with $ or containing . from req.body, req.query, and req.params recursively, preventing operator injection payloads.

Backend Source Code: src/middleware/sanitizeInput.js

const stripDangerousKeys = (value) => {
  if (Array.isArray(value)) {
    return value.map(stripDangerousKeys);
  }

  if (value !== null && typeof value === 'object') {
    const cleanObject = {};
    for (const [key, nestedValue] of Object.entries(value)) {
      if (key.startsWith('$') || key.includes('.')) {
        continue;
      }
      cleanObject[key] = stripDangerousKeys(nestedValue);
    }
    return cleanObject;
  }

  return value;
};

export const sanitizeInput = (req, res, next) => {
  if (req.body && typeof req.body === 'object') {
    req.body = stripDangerousKeys(req.body);
  }
  if (req.query && typeof req.query === 'object') {
    req.query = stripDangerousKeys(req.query);
  }
  if (req.params && typeof req.params === 'object') {
    req.params = stripDangerousKeys(req.params);
  }
  next();
};

Step 3: Secure the User Model with Salted Hashing & Hidden Hash Field

Backend Source Code: src/models/User.js

import mongoose from 'mongoose';
import bcrypt from 'bcryptjs';

const userSchema = new mongoose.Schema(
  {
    name: {
      type: String,
      required: true,
      trim: true,
      minlength: 2,
      maxlength: 80
    },
    email: {
      type: String,
      required: true,
      unique: true,
      lowercase: true,
      trim: true
    },
    passwordHash: {
      type: String,
      required: true,
      select: false
    },
    role: {
      type: String,
      enum: ['member', 'admin'],
      default: 'member'
    }
  },
  { timestamps: true }
);

userSchema.methods.verifyPassword = async function (candidatePassword) {
  return bcrypt.compare(candidatePassword, this.passwordHash);
};

const User = mongoose.model('User', userSchema);

export default User;

Backend Source Code: src/controllers/authController.js

import bcrypt from 'bcryptjs';
import User from '../models/User.js';

const toPublicUser = (userDoc) => ({
  id: userDoc._id,
  name: userDoc.name,
  email: userDoc.email,
  role: userDoc.role,
  createdAt: userDoc.createdAt
});

export const register = async (req, res, next) => {
  try {
    const { name, email, password } = req.body;

    if (typeof name !== 'string' || name.trim().length < 2) {
      return res.status(400).json({ status: 'fail', message: 'Valid name is required.' });
    }

    if (typeof email !== 'string' || !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email.trim())) {
      return res.status(400).json({ status: 'fail', message: 'Valid email is required.' });
    }

    if (typeof password !== 'string' || password.length < 10 || password.length > 128) {
      return res.status(400).json({
        status: 'fail',
        message: 'Password must be between 10 and 128 characters.'
      });
    }

    const normalizedEmail = email.trim().toLowerCase();
    const existing = await User.findOne({ email: normalizedEmail });
    if (existing) {
      return res.status(409).json({ status: 'fail', message: 'Unable to register with these details.' });
    }

    const rounds = Number(process.env.BCRYPT_ROUNDS) || 12;
    const passwordHash = await bcrypt.hash(password, rounds);

    const createdUser = await User.create({
      name: name.trim(),
      email: normalizedEmail,
      passwordHash,
      role: 'member'
    });

    return res.status(201).json({
      status: 'success',
      data: toPublicUser(createdUser)
    });
  } catch (err) {
    return next(err);
  }
};

export const login = async (req, res, next) => {
  try {
    const { email, password } = req.body;

    if (typeof email !== 'string' || typeof password !== 'string') {
      return res.status(400).json({ status: 'fail', message: 'Email and password must be strings.' });
    }

    const user = await User.findOne({ email: email.trim().toLowerCase() }).select('+passwordHash');

    const isValid = user ? await user.verifyPassword(password) : false;

    if (!user || !isValid) {
      return res.status(401).json({
        status: 'fail',
        message: 'Invalid email or password.'
      });
    }

    return res.status(200).json({
      status: 'success',
      data: toPublicUser(user)
    });
  } catch (err) {
    return next(err);
  }
};

Step 5: Enforce Ownership (Prevent BOLA) in Note Controller

Backend Source Code: src/controllers/noteController.js

import mongoose from 'mongoose';
import Note from '../models/Note.js';

export const getMyNote = async (req, res, next) => {
  try {
    const { id } = req.params;
    if (!mongoose.isValidObjectId(id)) {
      return res.status(400).json({ status: 'fail', message: 'Invalid note ID.' });
    }

    const note = await Note.findById(id).select('-__v');
    if (!note) {
      return res.status(404).json({ status: 'fail', message: 'Note not found.' });
    }

    const isOwner = note.ownerId.toString() === req.user.id;
    const isAdmin = req.user.role === 'admin';

    if (!isOwner && !isAdmin) {
      return res.status(403).json({
        status: 'fail',
        message: 'You do not have permission to access this note.'
      });
    }

    return res.status(200).json({ status: 'success', data: note });
  } catch (err) {
    return next(err);
  }
};

Step 6: Harden Global Express App Setup

Backend Source Code: src/app.js

import express from 'express';
import helmet from 'helmet';
import { sanitizeInput } from './middleware/sanitizeInput.js';
import authRoutes from './routes/authRoutes.js';
import noteRoutes from './routes/noteRoutes.js';

const app = express();

app.disable('x-powered-by');
app.set('trust proxy', 1);

app.use(helmet());
app.use(express.json({ limit: '10kb' }));
app.use(express.urlencoded({ extended: false, limit: '10kb' }));
app.use(sanitizeInput);

app.use('/api/v1/auth', authRoutes);
app.use('/api/v1/notes', noteRoutes);

app.all('*', (req, res) => {
  res.status(404).json({ status: 'fail', message: 'Endpoint not found.' });
});

app.use((err, req, res, next) => {
  const statusCode = err.statusCode || 500;
  res.status(statusCode).json({
    status: statusCode < 500 ? 'fail' : 'error',
    message: process.env.NODE_ENV === 'production' && statusCode === 500 ? 'Internal server error.' : err.message
  });
});

export default app;

Real-World Use Cases

1. Multi-Tenant Patient or Student Portals

Checking resource ownership (record.ownerId === req.user.id) stops a logged-in student from reading another student's grades simply by incrementing a numeric or ObjectId URL parameter.

2. Preventing Login Bypass via NoSQL Injection

Enforcing typeof email === 'string' and stripping $ keys prevents attackers from sending JSON objects like { "$ne": null } to trick findOne() into returning the first admin account.

3. Protecting User Credentials After a Database Leak

Salted bcrypt or scrypt hashing ensures that even if an attacker obtains a database backup, plaintext user passwords remain protected against rainbow-table and brute-force cracking.

4. Supply-Chain Hygiene in CI/CD Pipelines

Running npm audit and installing dependencies via npm ci (which strictly honors package-lock.json) blocks unexpected vulnerable dependency upgrades in production deployments.

Common Mistakes & API Security Checklist

Common Security Mistakes

  • Relying only on browser-side validation: HTML required attributes and frontend JavaScript checks can be bypassed in 2 seconds with curl. Server validation is mandatory.
  • Using SHA-256 for passwords: Fast hashes make offline cracking trivial. Always use slow salted algorithms (bcrypt, argon2, or scrypt).
  • Setting role: req.body.role during signup: Allows any visitor to register as an administrator. Hardcode role: 'member' on public signup.
  • Skipping ownership checks after authentication: Authentication proves who you are; it does not prove you own /api/v1/orders/999.
  • Committing .env once and deleting it later: Secrets remain in Git commit history forever—rotate any exposed credential immediately.

Production API Security Checklist

  • helmet() registered and x-powered-by disabled.
  • Body parser limits configured (e.g., limit: '10kb').
  • Strict type validation + NoSQL operator sanitization enabled.
  • Passwords hashed with salted bcrypt/argon2/scrypt and marked select: false.
  • Explicit allow-listing on create/update inputs (no raw req.body spreads).
  • Least privilege enforced on roles, ownership checks (anti-BOLA), and DB user permissions.
  • Neutral auth error messages + zero stack traces leaked in production.
  • .env gitignored; package-lock.json committed; npm audit clean.

Short-Answer Questions

Formulate your answer carefully before opening each model explanation.

1. What is the difference between input validation and input sanitization?

Validation verifies that incoming data meets strict rules (type, format, length, allowed values) and rejects invalid payloads with 400/422. Sanitization cleans or strips dangerous constructs (such as removing $ and . keys to stop MongoDB operator injection) before processing.

2. Explain how Broken Object Level Authorization (BOLA) occurs and how to prevent it.

BOLA occurs when an authenticated endpoint fetches or mutates a resource by :id without verifying that the authenticated user actually owns or is authorized for that specific record. Prevent it by checking ownership (doc.ownerId.equals(req.user.id)) or filtering queries by both _id and ownerId.

3. Why is express.json({ limit: '10kb' }) important for API security?

Capping request body sizes protects server memory and CPU against oversized JSON payloads that could otherwise slow down or crash the Node.js process.

4. How does committing package-lock.json and running npm audit support dependency hygiene?

package-lock.json pins exact deterministic dependency versions and checksums across environments, while npm audit scans the dependency tree against known vulnerability advisories so outdated packages can be patched.

5. What does "least privilege" mean for both API users and database connections?

API users should only receive minimum default roles and access only records they own or are permitted to view. Database connections should use dedicated credentials limited strictly to the single application database with only needed read/write privileges—never cluster root admin credentials.
